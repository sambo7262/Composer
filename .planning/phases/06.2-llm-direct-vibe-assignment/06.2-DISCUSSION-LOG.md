## Pass 1 batching strategy

Claude framed the cost / quality tradeoff with a back-of-envelope table at
600 rated tracks on Sonnet 4.6 (~3000-token cached system prompt, ~80
tokens per-track input, ~25 tokens per-track output).

| Option | Calls | Cost est | Pros | Cons | Selected |
|--------|-------|----------|------|------|----------|
| One big call (~600 tracks) | 1 | ~$0.55 | Cheapest; single cache build | Output ≈15k tokens, near Sonnet 4.6 default ceiling; one bad parse fails the library; no retry granularity; no progress UI | |
| Medium serial (50/call) | 12 | ~$0.40 | Cache hits 11× | Slightly more wall-clock; "less quality per call" headroom | |
| Medium parallel (50/call, ~3 concurrent) | 12 | ~$0.40 | Fastest wall-clock | First call must seed cache; LLMUsage write races; not worth it on a NAS | |
| Small serial (~25/call) | 24 | ~$0.45 base, ~$1.20 with reason field | Tightest per-track attention; smallest retry blast radius | More cache reads (still cheap) | ✓ |

**User's choice:** "Because the costs are so low, we should go for quality
here not speed — what would you recommend? Anything under $3 is fine."

Claude's quality-leaning recommendation set (all accepted):
- 25 tracks per batch (D-01)
- Strict serial execution (D-02)
- Required `reason` field per track (D-03)
- Vibe-definition preamble call (D-04)
- No extended thinking on Pass 1 (D-05)
- Retry-once per batch on validation failure (D-06)
- Output cap ≈ 3000 tokens per batch (D-07)

**User's notes:** "I'm less concerned about iterations as long as the
initial requests are of high quality — so I'm not worried about the issues
you are flagging — let's get it right the first time considering my vibes
aren't complex." Confirmed acceptance of the visible "Defining vibes…" UI
step from the preamble call AND the required reason field (no opt-out).

|--------|-------------|----------|

| Option | Description | Selected |
|--------|-------------|----------|
| Strict-both `strong` rubric | Requires artist signal AND audio-feature alignment for `strong` | ✓ |
| Loose-OR `strong` rubric | Either signal alone is sufficient for `strong` | |

| Option | Description | Selected |
|--------|-------------|----------|
| "Uncertainty is encouraged" framing in prompt | Explicit permission slip shifting LLM away from over-confidence | ✓ |

**User's choice:** "Yes to all three, strict-both"

**Notes:** Pass 2 trigger is locked by VIBE-14 to `weak OR uncertain`. The
strict-both rubric biases toward more Pass 2 traffic (~20-30% of tracks
estimated); user explicitly traded off Pass 2 cost for `strong`-confidence
quality.

## Deferred Ideas

- **Localized Pass 1 re-run on refinement split/add** — explicitly punted
  (D-23); revisit if user testing shows quality regression on refinement.
- **Periodic LLM re-eval job for `Vibe.centroid_*` drift** — `slot_track`
  uses distance against LLM-derived centroids; a periodic correction job
  could prevent drift but is out of scope. v2.1 candidate.
- **Self-consistency / dual-call Pass 1** — doubles cost; only justified if
  accuracy targets aren't hit at the locked design.
- **Sub-day archive suffix `(archived YYYY-MM-DD HH:MM)`** — date-only is
  sufficient for normal user behavior; bump precision only if multiple
  same-day resets become a real issue.
- **`time-of-day` extension on `archive_playlist`** — same as above.
- **Per-vibe member-count guardrails / warnings** — if the LLM persistently
  assigns 90% of tracks to one vibe, surface a warning. Out of scope at
  Phase 6.2; the strict-both rubric (D-09) + Pass 2 (D-12..D-17) should
  already discourage this failure mode.
- **`Re-cluster` button using the new pipeline** — carries forward
  automatically via D-22; verify in UAT, no new code needed.
