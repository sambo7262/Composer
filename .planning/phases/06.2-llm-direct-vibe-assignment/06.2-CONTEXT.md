# Phase 6.2: LLM-Direct Vibe Assignment - Context

**Gathered:** 2026-05-12
**Status:** Ready for planning

<domain>
## Phase Boundary

Phase 6.2 replaces k-means *cluster membership* with **LLM-direct zero-shot
assignment** of each rated track to a user-typed vibe. Two passes:

1. **Pass 1 (assign).** Batched per-track LLM call. The LLM receives a per-vibe
   "definition" preamble (one-line description per user-typed vibe) plus, for
   each track, `(title, artist, genre, energy, tempo, danceability, valence)`.
   It returns the chosen vibe name + a confidence grade
   (`strong | weak | uncertain`) + a short reason string per track.

2. **Pass 2 (peer-context boundary review).** Tracks graded `weak` or
   `uncertain` in Pass 1 are re-sent to the LLM along with the *peer-context*
   of their top 2 candidate vibes — i.e., the 10 most-representative tracks
   already graded `strong` for each candidate. The LLM picks a final vibe
   with the peer list visible. Pass 2's verdict is a final commitment, not
   a re-graded one; the wizard surfaces a "confidence chip" on the proposal
   card for any track that went through Pass 2 (the original Pass 1 grade is
   what the chip reflects).

K-means survives only as a **centroid generator for the Pass 1 prompt
context** — its cluster summaries (per-cluster centroid + top artists + top
genres + sample tracks) feed the LLM's mental model of how the feature space
breaks down. **K-means labels are discarded.** Final `Vibe.centroid_*` columns
stored in SQLite are recomputed as the mean of LLM-assigned members per vibe
(membership-faithful centroids).

Audio features still flow into the LLM prompt as a **tiebreaker** for tracks
with low artist recognition. K-means' geometric clustering of the feature
space gives the LLM scaffolding without dictating outcomes.

Phase 6.2 also implements **WIZ-08 — user-triggered "Start Over" reset.** A
button in settings wipes vibe + wizard state (`Vibe`, `TrackVibe`,
`ManagedPlaylist`, `SlotInLog`, `SetupState` including `draft_proposals_json`)
and archives existing `Composer · {name}` Plex playlists with a date-stamped
`(archived YYYY-MM-DD)` suffix to avoid collisions on repeated resets.
`ServiceConfig` rows for Plex / Anthropic / Lidarr are explicitly preserved.
The reset is naturally idempotent — a second call finds nothing to archive
and zero rows to wipe.

Phase 6.2 does NOT touch:

- The Phase 6.1 first-deploy migration (`run_phase_61_migration`) — that
  remains a one-shot lifespan startup. WIZ-08 reset is a separate,
  user-triggered, repeatable operation.
- The post-wizard slot-in hot path (`vibe_service.slot_track`) — newly-rated
  tracks still auto-slot via centroid distance against the LLM-derived
  centroids. No LLM call on individual rating events (latency + cost).
- The re-cluster commit path (`api_vibes._recluster_commit` / D-21 from
  Phase 6) — D-21 consumes whatever `VibeProposalSet` is in
  `SetupState.draft_proposals_json`; the producer of that set changes (6.2's
  LLM-direct pipeline), the consumer does not.
- The Phase 6.1 conversational refinement loop (`refine_proposals`) — it
  carries forward unchanged. Merge / rename / drop run as cheap symbolic
  operations on the proposal set; **split and add are punted** (do not
  trigger a localized Pass 1 re-run in this phase — accept some accuracy
  drift on refinement if the user uses it). Documented as known gap.

</domain>

<decisions>
## Implementation Decisions

### Pass 1 — batching & assign

- **D-01: Batch size = 25 tracks per call.** Tighter than 50 to preserve the
  LLM's per-track attention budget. Resists the "default to most-populous
  vibe on long lists" failure mode. For 600 rated tracks → 24 batches.
- **D-02: Strict serial execution.** First call seeds the Anthropic prompt
  cache (1h TTL, per Phase 5 / Pitfall 9); batches 2..24 hit the cache. No
  parallelism — avoids LLMUsage write races, simplifies the wizard progress
  UI, and the cache must build before any other batch can hit it.
- **D-03: Required `reason` field per track in the response schema.** Short
  free text (5-15 words target, e.g. "synth-heavy ambient texture, low
  energy"). REQUIRED, not optional — optional fields get omitted under
  output pressure. Forces explicit reasoning, surfaces in `/debug/vibes` for
  free, and feeds Pass 2's input as the "why Pass 1 picked this" signal.
- **D-04: Vibe-definition preamble call.** Before any batch assignments, one
  LLM call (purpose=`vibe_definitions_preamble`): "User typed these N vibe
  names — write 1 sentence per vibe describing what kind of track belongs
  there." The returned per-vibe definitions are baked into the cached system
  prompt of every subsequent batch. Anchors the LLM against drift between
  batches and against vague names ("synth heavy" vs "late night drive").
  Cost ~$0.02. Adds ~5s to wizard latency — accepted (user prefers quality
  over iteration speed).
- **D-05: NO extended thinking on Pass 1.** For parallel batch classification
  the marginal accuracy bump doesn't justify the cost — thinking tokens
  don't share across tracks in a batch and scale linearly per call. Save
  thinking budget for Pass 2 (see D-12).
- **D-06: Retry-once per batch on validation failure.** Mirrors the
  Phase 6.1 LLMVibeMappingResponse pattern: slim permissive LLM schema →
  strict canonical model conversion + retry-once with corrective addendum.
  Retry is batch-scoped — never re-issue the whole library on a single
  bad batch.
- **D-07: Output token cap per batch ≈ 3000 tokens.** Leaves comfortable
  margin under Sonnet 4.6's default ceiling. At 25 tracks × ~80 output
  tokens per track (vibe_name + grade + reason) ≈ 2000 tokens, fits cleanly.

### Pass 1 — confidence grading rubric

- **D-08: LLM self-grades.** Server-side post-hoc grading from a numeric
  score is not workable — LLMs don't emit calibrated probabilities. Self-
  grading with a clear rubric, validated by Pass 2 peer review, is the
  durable design.
- **D-09: Rubric definitions (in the cached system prompt):**
  - **`strong`** — Artist is a known fit for this vibe **AND** audio features
    clearly align with the vibe's definition. Or genre is a textbook match
    AND features align. **Strict-both** required — one signal isn't enough
    to claim `strong`. (Confirmed during discuss.)
  - **`weak`** — Exactly one signal aligns. Features look right but artist
    is unknown to the LLM, or artist is recognized but features are
    average. Track *probably* belongs here; peer comparison would settle it.
  - **`uncertain`** — No clear signal. Features are middle-of-the-road,
    artist not recognized, genre absent or ambiguous, or the track could
    fit two vibes equally.
- **D-10: "Uncertainty is encouraged" framing in the prompt.** Explicit
  permission slip in the cached system prompt: *"Marking 'uncertain' is
  encouraged when the signal is mixed — uncertain tracks get reviewed in a
  second pass with more context. Over-confident wrong answers cost more
  than honest uncertainty."* Shifts the LLM away from default
  over-confidence. Single line, large effect on grading honesty.
- **D-11: Pass 2 trigger = `weak` OR `uncertain`.** Per VIBE-14. Expected
  Pass 2 traffic at user's library scale: ~20-30% of tracks → ~120-180
  boundary tracks for a 600-track library. Strict-both `strong` rubric will
  bias toward more Pass 2 traffic; accepted (the user is paying for
  accuracy).

### Pass 2 — boundary review

- **D-12: Extended thinking ON for Pass 2.** ~1024 thinking tokens per call.
  Each Pass 2 decision is deliberate (boundary case + peer context); the
  thinking budget earns its keep. Cost ~$0.30-0.60 total across Pass 2.
- **D-13: Candidate vibes per Pass 2 track = top 2.** Pass 1's pick is
  candidate #1. The alternate is the next-closest vibe by server-computed
  centroid distance (z-score normalized features against the k-means /
  pre-Pass-1 centroids). Always 2 candidates; always includes Pass 1's pick
  so the LLM can vindicate or override its earlier call.
  - Edge case: if Pass 1's pick is *third*-closest by distance (rare —
    happens when the LLM strongly preferred a non-feature-aligned vibe due
    to artist or genre signal), candidate set becomes `{Pass 1's pick,
    closest by centroid}`. Still 2 candidates.
- **D-14: Peer count per candidate = 10 strong-graded tracks.** Picked from
  `strong`-graded Pass 1 assignments only (not weak / uncertain — those
  aren't anchors), sorted by centroid distance ascending so the LLM sees
  the *most representative* tracks first. 10 is the sweet spot — enough
  variety to recognize the vibe's character, not enough to bury signal.
- **D-15: Peers live in the cached system prompt for the entire Pass 2
  phase, not per-call.** All N vibes × 10 peers ≈ 5000 tokens for 5 vibes.
  One cache build, every Pass 2 batch hits it (well above the
  SONNET_4_6_CACHE_MIN_TOKENS threshold). User prompt is per-track:
  features + Pass 1 verdict + Pass 1 reason + which two candidates this
  track sits between.
- **D-16: Pass 2 batch size = 15 tracks per call.** Smaller than Pass 1
  (D-01) because each user-prompt entry is denser. ~7-12 calls total for
  100-180 boundary tracks. Strict serial. Retry-once granularity.
- **D-17: Pass 2 output is a final commitment.** Response per track:
  `{track_index, final_vibe_name, reason}`. No grade re-issued. The
  wizard's "confidence chip" surfaces the *original Pass 1 grade* on
  proposal cards for tracks that went through Pass 2 — chip semantics is
  "this track was a boundary call, here's why" with the reason on tap.

### Pipeline integration & code organization

- **D-18: Replace `vibe_clusterer.map_user_vibes_to_clusters` outright.** No
  sibling function, no `_v2` suffix. The existing function's mental model
  (k-means produces membership) is precisely the bug being fixed; keeping
  it around is dead code. Rename to `assign_tracks_to_user_vibes` (or
  similar — naming is Claude's discretion) and rewrite the body. Single
  caller in `app/routers/api_setup.py /propose/init` gets the import +
  call-site update.
- **D-19: K-means runs once at the start of Pass 1, for centroids only.**
  Reuse the existing k-means infrastructure in `vibe_clusterer.py`
  (`_pick_best_k` with `forced_k=N`) to produce N cluster summaries
  (centroid + top artists + top genres + sample tracks) that feed the
  cached Pass 1 system prompt. **K-means labels are discarded.** This
  enforces the "k-means stays as a centroid generator only" success
  criterion at the code level. Add a code-review check: no read of
  `kmeans.labels_` for membership assignment after Pass 1's prompt
  construction.
- **D-20: Final `Vibe.centroid_*` is computed from LLM-assigned members.**
  After Pass 1 + Pass 2 finalize per-track membership, server recomputes
  per-vibe centroid as `mean(features of LLM-assigned members)` and stores
  in `Vibe.centroid_energy/tempo/danceability/valence`. This makes stored
  centroids faithful summaries of the LLM's choices — consistent with what
  `slot_track` will measure against.
- **D-21: `slot_track` stays distance-based against LLM-derived centroids.**
  No change to the Phase 6 D-15 slot-in hot path. Newly-rated tracks
  auto-slot via z-score-normalized 4-D Euclidean distance to
  `Vibe.centroid_*`. Latency stays ~10ms; no LLM call per rating event.
  Deliberate compromise: the LLM-derived centroid (D-20) is a faithful
  summary of what the LLM put in each vibe, so distance to that centroid
  is a reasonable proxy for "would the LLM agree?". If quality drifts as
  the user adds many new ratings outside the LLM's groupings, a future
  phase can add a periodic LLM re-eval job. Phase 6.2 scope = initial
  pass + re-cluster only. Document the approximation.
- **D-22: Re-cluster commit (Phase 6 D-21) wires unchanged.** The
  producer of `VibeProposalSet` (now LLM-direct) changes; the consumer
  (`/api/vibes/recluster/commit` diff-based reconciliation) does not.
  Manual-override stickiness (Phase 6 D-22) also carries forward — manual
  `TrackVibe.assigned_by='manual'` rows survive 6.2's pipeline because
  the LLM never sees those rows in the rated-track aggregate and the
  post-pipeline membership-merge step preserves them.
- **D-23: Refinement loop (`refine_proposals`) is OUT OF SCOPE for 6.2's
  pipeline rewrite.** Merge / rename / drop / keep operate on proposal
  structure with cheap symbolic operations (union members for merge,
  rename in place, etc.); `Vibe.centroid_*` is recomputed from the
  resulting membership. **Split and add are PUNTED — they do NOT trigger
  a localized Pass 1 re-run in 6.2.** Refinement carries forward from
  Phase 6.1 with whatever quality the existing implementation provides;
  if accuracy drifts on refinement, address in a later phase. Document
  the known gap in PLAN.md.

### WIZ-08 — "Start Over" reset

- **D-24: Single entry point — settings page only.** One button in the
  Vibes section of settings, **"Start Over"**, visually distinct as
  destructive (red border or similar — UI-SPEC level). Visible only when
  `Vibe.count() > 0`. No in-wizard entry — the existing `/api/setup/reset`
  (Phase 6.1) stays as the lighter "wipe SetupState, go back to Step 1"
  path for mid-wizard restarts and serves a different need.
- **D-25: Confirm-modal copy.** Required wording (exact text is Claude's
  discretion for tone polish, but content is locked):

  ```
  Start Over?

  This will:
  • Archive your current Composer playlists in Plex (renamed with an
    "(archived YYYY-MM-DD)" suffix — they remain in Plex for you to
    clean up in Plexamp)
  • Clear all vibe assignments and wizard state in Composer
  • Restart the setup wizard from Step 1

  Your Plex, Anthropic, and Lidarr credentials are preserved.

  This cannot be undone.

  [ Cancel ]   [ Start Over ]    ← red
  ```

- **D-26: Archive suffix uses a date stamp — `(archived YYYY-MM-DD)`.**
  Phase 6.1 first-deploy migration's plain `(archived)` stays because it's
  one-shot. WIZ-08 reset is repeatable; without a timestamp, repeated
  resets create multiple "Composer · Workout (archived)" playlists in Plex.
  Implementation: extend `plex_playlist_service.archive_playlist` with an
  optional `suffix` arg, default unchanged (preserves Phase 6.1 behavior).
  WIZ-08 caller passes a date-stamped suffix. Date-only (no time-of-day) —
  sub-day collision is overkill.
- **D-27: No `MigrationLog` gate. Single in-handler atomic transaction.**
  `MigrationLog` is for one-shot startup migrations (Phase 6.1); WIZ-08
  is user-triggered and repeatable. New endpoint `POST /api/setup/start-over`:
  1. Read all `ManagedPlaylist` rows.
  2. For each: archive on Plex with date suffix (D-26). **Best-effort
     with the SAME tight-except pattern as Phase 6.1 migration** — catch
     `plexapi.exceptions.PlexApiException`, `httpx.HTTPError`,
     `PermissionError`, `TypeError`. Log + continue on per-playlist
     failure. **NEVER `except Exception`.**
  3. DB wipe in FK-safe order: `SlotInLog` → `TrackVibe` →
     `ManagedPlaylist` → `Vibe`.
  4. Reset `SetupState` id=1: `step="rating_source"`,
     `draft_proposals_json=""`, `refinement_turn_count=0`,
     `last_llm_call_id=None`, `recluster_mode=False`, `completed_at=None`.
  5. `UPDATE Track SET pending_slot_in=0 WHERE pending_slot_in=1`.
  6. Return `Response(status_code=204, headers={"HX-Redirect": "/setup"})`.

  Steps 3-5 share one `Session.commit()`. Plex archive failures (step 2)
  must not roll back the DB wipe — the user shouldn't be stuck if Plex is
  unreachable.
- **D-28: `ServiceConfig` is explicitly NOT touched.** No DELETE, no UPDATE
  in the reset endpoint. Mandatory regression test
  `test_start_over_preserves_serviceconfig_rows` asserts plex / anthropic /
  lidarr `ServiceConfig` rows survive a reset call.
- **D-29: Idempotency is naturally emergent — no gate required.** Success
  criterion #6: "running reset twice in a row is a no-op on the second
  call." Second call finds zero `ManagedPlaylist` rows → zero Plex
  archive calls; empty-table DELETEs → 0 rows affected; `SetupState`
  already at `rating_source` → idempotent update; → 204.
- **D-30: Required test suite for WIZ-08:**
  - `ServiceConfig` (plex/anthropic/lidarr) rows preserved across reset.
  - All five tables wiped: `Vibe`, `TrackVibe`, `ManagedPlaylist`,
    `SlotInLog` empty; `SetupState` reset to defaults.
  - `Track.pending_slot_in` cleared on every previously-flagged row.
  - Archive suffix is `(archived YYYY-MM-DD)`, not `(archived)`.
  - Second consecutive reset call is a no-op (no Plex calls, no DB writes
    that change state).
  - Plex archive failure for one playlist doesn't block the DB wipe or
    subsequent archive calls.
  - `SetupState.draft_proposals_json` is empty string post-reset (covers
    the private-browser leak criterion).

### LLM call architecture

- **D-31: New `purpose` values for `LLMUsage` segmentation:**
  - `"vibe_definitions_preamble"` — D-04 single preamble call.
  - `"vibe_assign_pass1"` — D-01..D-07 batch assignments (one per batch).
  - `"vibe_assign_pass2"` — D-12..D-17 boundary review (one per batch).
  - The legacy `"vibe_clustering_user_led"` (Phase 6.1) is RETIRED with
    the function rewrite (D-18). Existing `"vibe_clustering_refine"` and
    `"vibe_clustering_recluster"` survive — refinement and re-cluster
    still call `refine_proposals` (D-23).
- **D-32: Cost ceiling per full library re-cluster ≤ $1.50 measured target;
  ≤ $3.00 acceptance ceiling.** ROADMAP / VIBE-13 specify $1.50; user
  approved up to $3 for quality during discuss. Expected cost at 600
  rated tracks with the above decisions: preamble $0.02 + Pass 1 ~$1.20
  + Pass 2 ~$0.30-0.60 ≈ **$1.50-1.80 per re-cluster**. Comfortable under
  $3 ceiling, leaves room for occasional retries. Measured via the
  existing `LLMUsage` table aggregated by `purpose` LIKE `vibe_%`.
- **D-33: Slim-schema pattern carries forward.** New Pydantic shapes
  (Claude's discretion on exact names — likely
  `LLMVibeAssignmentResponse`, `LLMVibeBoundaryResponse`) follow the
  established LLMVibeProposal / VibeProposalSetLLMResponse permissive →
  canonical pattern from Phase 6.1 quick-260510-i1q. Defensive tests
  required on the slim schemas to fail loudly if server-controlled
  fields leak onto LLM-facing models.

<specifics>
## Specific Ideas

- **The user's framing of "quality first, iteration cost secondary."** Budget
  approved up to $3 per re-cluster (vs the ROADMAP's $1.50 target). This
  unlocks: smaller Pass 1 batches (D-01 = 25), required reason field (D-03),
  preamble call (D-04), extended thinking on Pass 2 (D-12), larger peer
  context (D-14 = 10), strict-both `strong` rubric (D-09). Without the budget
  headroom several of those decisions would have flipped toward speed.

- **"My vibes aren't complex" signal.** Justifies punting Pass 1 re-runs on
  refinement (D-23 split/add): the user is unlikely to engage the
  refinement loop heavily, and "merge/rename/drop" symbolic operations
  cover the common cases.

- **"Get it right the first time" pressure.** Drives the preamble + strict
  rubric + extended thinking on Pass 2 combination — together these are
  the three highest-leverage accuracy moves at this budget.

- **Date-stamped archive suffix `(archived YYYY-MM-DD)`** — the specific
  detail the user agreed to that prevents Plex playlist name collisions on
  repeated WIZ-08 resets. Phase 6.1's plain `(archived)` was sufficient for
  one-shot first-deploy; WIZ-08's repeatability needs the timestamp.

- **Settings-only WIZ-08 entry point** — keeps the destructive operation
  behind one consistent surface. No mid-wizard entry to confuse users with
  two different reset semantics.

</specifics>

<deferred>
## Deferred Ideas

- **Localized Pass 1 re-run on refinement split/add.** Phase 6.2 explicitly
  punts this (D-23). If user testing shows refinement quality regresses
  noticeably when splitting or adding vibes, address in a follow-up phase
  with a localized Pass 1 call on the affected subset. v2.1 candidate.

- **Periodic LLM re-eval job for centroid drift.** `slot_track` (D-21) uses
  distance-based auto-slot against LLM-derived centroids. If many newly-
  rated tracks slot to vibes the LLM wouldn't have picked, a daily/weekly
  batched LLM re-eval could correct drift. v2.1 candidate; surface a
  drift indicator on `/debug/vibes` if it becomes a real problem.

- **Self-consistency / dual-call Pass 1.** Call Pass 1 twice with the same
  input, take majority vote. Doubles cost; non-trivial implementation.
  Only worth it if accuracy targets aren't hit at this design. v2.x.

- **Sub-day archive collision (`(archived YYYY-MM-DD HH:MM)`)** — date-only
  collision is rare enough that minute precision is overkill. Revisit if
  the user reports being unable to distinguish multiple same-day resets.

- **Time-of-day extension on `archive_playlist` suffix.** Same as above.

- **`Re-cluster` button using the new pipeline.** Carries forward
  automatically via D-22 — the existing `/api/vibes/recluster/start` +
  `/api/vibes/recluster/commit` endpoints now produce a `VibeProposalSet`
  from the LLM-direct pipeline. No new code needed; verify in UAT.

- **Per-vibe member-count budget enforcement.** If the LLM persistently
  assigns 90% of tracks to one vibe, surface a warning to the user and
  offer "rename or re-cluster". Out of scope; the user's strict-both
  rubric (D-09) + Pass 2 peer review already discourage this failure mode.

</deferred>
