## Summary

The Anthropic API for extended thinking is **actively migrating away from
manual `budget_tokens`** on Sonnet 4.6 / Opus 4.6 toward an `adaptive`
thinking mode. Manual mode still works on Sonnet 4.6 (deprecated, not
removed), but adaptive is the recommended path — and adaptive avoids
several pitfalls the manual D-12 specification would hit, in particular
the requirement that `budget_tokens >= 1024` AND `budget_tokens < max_tokens`
(which collides badly with our Pass 2 small-batch design).

Thinking output appears as a **separate `thinking` content block that
precedes the text block** in `response.content`. The existing
`anthropic_client.py` parser does `response.content[0].text` —
**this breaks the moment thinking is enabled**, because `content[0]` is now
a `ThinkingBlock` with no `.text` attribute. The minimal correct patch is
to iterate `response.content` and pick the first block where
`block.type == "text"`.

Thinking tokens are **billed at the output-token rate** and rolled into
`response.usage.output_tokens` — there is no separate
`thinking_tokens` field. Cost segmentation in `LLMUsage` therefore continues
to work without schema changes; thinking cost is simply baked into the
output-tokens line item for Pass 2 calls.

Prompt-caching interaction is favorable: **system prompt caches survive
thinking changes**. Message-level caches do not, but Composer doesn't use
message-level caching. The 1h-TTL system-prompt cache (Phase 5 Pitfall 9)
stays hot across all Pass 2 calls regardless of thinking mode.

**Primary recommendation:** Switch D-12 from manual
`{"type": "enabled", "budget_tokens": 1024}` to adaptive
`{"type": "adaptive"}` with no `output_config.effort` override
(default `high`). Document the cost-control mechanism explicitly: cap via
`max_tokens` (already done — D-07's 3000-token ceiling applies). Patch
`call_with_structured_output` to (a) accept a `thinking_mode` parameter
with values `"off"` / `"adaptive"` (default `"off"` for backward
compatibility), (b) iterate `response.content` to find the text block
robustly, regardless of thinking state.

## 1. Anthropic Extended Thinking API on Sonnet 4.6

### 1.1 Two modes: `enabled` (manual, deprecated) vs `adaptive` (recommended)

| Mode | Config | Sonnet 4.6 Status |
|------|--------|-------------------|
| `enabled` (manual) | `{"type": "enabled", "budget_tokens": N}` where `N >= 1024` and `N < max_tokens` | [CITED: platform.claude.com/docs/en/build-with-claude/adaptive-thinking] **Deprecated but still functional**; will be removed in a future model release. |
| `adaptive` | `{"type": "adaptive"}` (optionally `+ output_config: {effort: "low" | "medium" | "high" | "max"}`) | [CITED: same] **Recommended.** Claude decides per-request whether to think and how deeply. |
| `disabled` (= absent) | omit the `thinking` param entirely, OR `{"type": "disabled"}` | Default. Existing behavior in `anthropic_client.py`. |

[VERIFIED: platform.claude.com/docs] On **Opus 4.7**, manual mode is
**rejected with a 400 error** — adaptive is the *only* supported mode. This
foreshadows where the platform is heading: any new code that uses manual
`budget_tokens` is on a clock. **Strong recommendation: use adaptive on
Sonnet 4.6 to avoid a near-term forced migration.**

CONTEXT.md D-12 currently specifies `~1024 thinking tokens per call` —
which is the **minimum** for manual mode. With adaptive, you don't specify
a token count; Claude picks. For boundary-review tasks the default `high`
effort almost-always-thinks, which is exactly what D-12 wants.

### 1.2 Response shape — thinking blocks come BEFORE text

[VERIFIED: platform.claude.com/docs/en/build-with-claude/extended-thinking]

```json
{
  "content": [
    {
      "type": "thinking",
      "thinking": "Let me analyze... peer track 3 has high energy / low valence...",
      "signature": "WaUjzkypQ2mU..."
    },
    {
      "type": "text",
      "text": "{\"assignments\": [...]}"
    }
  ]
}
```

The `ThinkingBlock` has **no `.text` attribute** — it has `.thinking` and
`.signature`. Therefore:

```python
# CURRENT code (anthropic_client.py:120) — BREAKS when thinking is enabled:
text = response.content[0].text.strip()
# AttributeError: 'ThinkingBlock' object has no attribute 'text'
```

The minimal correct patch:

```python
# Robust against thinking blocks, redacted_thinking blocks, future block types:
text_block = next(
    (b for b in response.content if b.type == "text"),
    None
)
if text_block is None:
    raise ValueError(
        f"Anthropic response had no text block (got types: "
        f"{[b.type for b in response.content]})"
    )
text = text_block.text.strip()
```

[VERIFIED: docs] Block types to anticipate:
- `"thinking"` — visible summarized reasoning (default `display: "summarized"` on Sonnet 4.6)
- `"redacted_thinking"` — encrypted reasoning when safety policy intervenes
- `"text"` — the final text response
- `"tool_use"` — only if tool use is wired (Composer doesn't use tools)

### 1.3 Billing

[CITED: platform.claude.com/docs/en/build-with-claude/adaptive-thinking#pricing]

- **Thinking tokens are billed at the output-token rate** ($15/Mtok on
  Sonnet 4.6).
- Thinking tokens are **rolled into `response.usage.output_tokens`** — there
  is NO separate field for thinking cost.
- Billed token count > visible token count. The full thinking is billed;
  the summarized thinking shown in the response is shorter (free).
- `display: "omitted"` reduces *latency* only, not cost.

**Implication for Composer:** `LLMUsage.output_tokens` already captures
all Pass 2 thinking cost. `_log_usage` math (lines 161-166 of
`anthropic_client.py`) needs no change. The dashboard query
`SELECT SUM(cost_estimate_usd) FROM llmusage WHERE purpose = 'vibe_assign_pass2'`
will give the correct total Pass 2 spend without segregating thinking
vs answer tokens — which we couldn't do anyway, because the API
doesn't return them separately.

### 1.4 Prompt caching interaction

[CITED: adaptive-thinking docs]

> **System prompts and tool definitions remain cached** regardless of
> thinking-mode changes. Message-level cache breakpoints break when
> switching between `adaptive` and `enabled`/`disabled` modes.

Composer's caching pattern (anthropic_client.py:86-92) places
`cache_control` ONLY on the **system message**, never on the user message.
Therefore:

- ✅ Cache hits on the system prompt persist across all Pass 2 calls,
  even with adaptive thinking enabled.
- ✅ Even if a future call mixes thinking-on and thinking-off batches
  (we don't — Pass 1 is uniformly off, Pass 2 is uniformly on), the
  system-prompt cache survives.
- ✅ The 1h TTL invariant (Pitfall 9) is untouched.

D-15's "Pass 2 peer context cached for the whole phase" continues to work.

### 1.5 `budget_tokens` constraints (if we kept manual mode)

[CITED: platform.claude.com/docs/en/api/messages — ThinkingConfigParam]

- `budget_tokens >= 1024` (minimum)
- `budget_tokens < max_tokens` (strict less-than)
- Maximum output across thinking + text is bounded by `max_tokens`

**This is a problem if we used manual mode with D-12's spec.** D-12 says
"~1024 thinking tokens per call" — the minimum. D-16 says Pass 2 is 15
tracks per batch. At 15 tracks × ~80 tokens/track answer = ~1200 answer
tokens. So if `budget_tokens=1024` and we want 1200 tokens of answer, we
need `max_tokens >= 2224` — fine, but tight.

With adaptive mode the constraint drops: Claude picks its own thinking
budget and the only ceiling is `max_tokens`. We set `max_tokens=3000`
(matching D-07's Pass 1 ceiling) and Claude will use whatever portion of
that is needed for thinking + answer.

[VERIFIED: docs] If `stop_reason: "max_tokens"` shows up in responses,
that means thinking ate too much of the budget — increase `max_tokens`
or lower `effort`. Worth logging in the parser to detect this failure mode.

### 1.6 Adaptive `effort` for classification tasks

[CITED: adaptive-thinking docs]

| Effort | Behavior on Sonnet 4.6 |
|--------|------------------------|
| `max` | Always thinks deeply, no constraints. |
| `high` (default) | Always thinks. Right level for "deliberate boundary case + peer context." |
| `medium` | May skip thinking for simple queries. |
| `low` | Minimizes thinking. Skips for simple tasks. |

For Pass 2 (boundary review with peer context), **default `high` is the
right choice** — every Pass 2 track IS by definition a boundary case, so
"always think" is exactly what we want. No `output_config.effort` override
needed; just `thinking={"type": "adaptive"}`.

### 1.7 Known JSON-output + thinking gotchas

[CITED: github.com/anthropics/anthropic-sdk-python/issues/1204]

Issue #1204 (Feb 2026) reports two bugs when combining **thinking +
structured output + TOOL USE**:
1. Sometimes returns thinking block + empty text block, no tool_use blocks.
2. Final text contains malformed JSON.

**Composer is NOT affected.** We do not use tool use; we parse JSON
directly from the text block via `model_validate_json`. The bugs are
specific to `messages.parse()` with `output_format=...` and tool_choice
constraints — none of which Composer touches.

The Composer pattern (free-text JSON response → `model_validate_json` with
`raw_decode` salvage) is the *workaround* that Issue #1204 recommends.
We're already on the safe path.

[ASSUMED] No additional JSON-format degradation observed when thinking is
enabled on a free-text JSON response. The thinking process is "warmup" for
the answer; the answer block is unchanged in structure. Confidence:
medium-high — this is the documented design intent and the SDK behavior in
practice, but not explicitly stated as a guarantee for JSON-output
workloads. **Mitigation:** the existing retry-once corrective-prompt
pattern (D-06) handles transient JSON-shape issues regardless of cause.

### 1.8 Streaming requirement

[VERIFIED: docs] Streaming is **optional**, not required. Composer's
non-streaming `messages.create(...)` works with thinking enabled.

### 1.9 Multi-turn / `signature` continuity

[CITED: docs] Sonnet 4.6+ **keeps thinking blocks in context** by default
across multi-turn conversations (older models stripped them). Composer
makes **single-shot calls** (one user prompt, one assistant response,
discard — no multi-turn within `call_with_structured_output`), so the
`signature` field and multi-turn-continuity machinery is **unused**. We
don't need to forward thinking blocks back into a follow-up call.

## 2. AnthropicClient Signature Impact

### 2.1 Backward-compat constraint

Existing callers MUST NOT regress:
- `vibe_clusterer.map_user_vibes_to_clusters` (Phase 6.1 user-led mapping)
- `vibe_clusterer.refine_proposals` (Phase 6 refinement)
- `taste_profile_service` (Phase 5 taste profile)

None of these use thinking. Default behavior must remain
`thinking` parameter absent → no thinking → existing response shape →
`response.content[0]` is a text block → current parser works as-is.

### 2.2 Recommended signature

```python
from typing import Literal

ThinkingMode = Literal["off", "adaptive"]

async def call_with_structured_output(
    self,
    system_prompt: str,
    user_prompt: str,
    response_model: Type[T],
    max_tokens: int = 1024,
    purpose: str = "unspecified",
    thinking: ThinkingMode = "off",  # NEW — D-12
) -> T:
    ...
    kwargs = {
        "model": self._model,
        "max_tokens": max_tokens,
        "system": [{
            "type": "text",
            "text": system_prompt,
            "cache_control": {"type": "ephemeral", "ttl": "1h"},
        }],
        "messages": [{"role": "user", "content": user_prompt}],
    }
    if thinking == "adaptive":
        kwargs["thinking"] = {"type": "adaptive"}
    response = await self._client.messages.create(**kwargs)
    ...
    # Robust text-block extraction (handles thinking-on AND thinking-off):
    text_block = next(
        (b for b in response.content if b.type == "text"),
        None,
    )
    if text_block is None:
        raise ValueError(
            f"Anthropic response missing text block (purpose={purpose}, "
            f"block types={[b.type for b in response.content]})"
        )
    text = text_block.text.strip()
    ...
```

**Why a `Literal` enum, not `bool` or `budget_tokens: int = 0`:**
- `bool` doesn't allow future expansion to `max`/`xhigh` effort or
  per-mode tuning if needed.
- `budget_tokens: int = 0` would lock us into the manual API that's
  being deprecated (§1.1).
- `Literal["off", "adaptive"]` reads cleanly at call sites: `thinking="adaptive"`.

**Why pass `thinking` only when it's "adaptive":**
- Keeps the request body byte-identical for existing callers (better
  prompt-cache stability than passing `{"type": "disabled"}`).
- Per §1.4, switching between absent / disabled / adaptive can affect
  message-level cache; though we don't cache messages, absent-when-off is
  the cleanest semantic.

### 2.3 Robust text-block extraction is a MANDATORY change

Even if a particular caller doesn't use thinking, **fixing the parser to
iterate over `response.content` is a one-line robustness win**: it
future-proofs against the SDK ever interleaving content block types
(e.g., a model update could add a metadata block before the text block).
The `response.content[0].text` indexing assumption is fragile.

The fix must be applied **in the same change** as adding `thinking`
support, NOT as a separate task. Doing it later means existing callers
silently break when they're upgraded to use thinking. Atomic.

### 2.4 LLMUsage logging — no change required

§1.3: thinking tokens are rolled into `response.usage.output_tokens`.
The cost calculation at `anthropic_client.py:161-166` is correct as-is:

```python
cost = (
    input_tokens * PRICING_INPUT_USD_PER_MTOK / 1_000_000
    + cache_creation_tokens * PRICING_CACHE_WRITE_1H_USD_PER_MTOK / 1_000_000
    + cache_read_tokens * PRICING_CACHE_READ_USD_PER_MTOK / 1_000_000
    + output_tokens * PRICING_OUTPUT_USD_PER_MTOK / 1_000_000
)
```

`output_tokens` already includes thinking. No new pricing constant. No
new column on `LLMUsage`. The Pass 2 `purpose='vibe_assign_pass2'` rows
will show higher avg cost-per-call than Pass 1 — that's the visible
thinking spend.

## 3. Pass 1 Batched Classification Best Practices

### 3.1 Output structure

CONTEXT.md D-01 / D-03 lock the structure:
```json
{
  "assignments": [
    {"track_index": 0, "vibe_name": "Workout", "grade": "strong", "reason": "synth-heavy ambient texture, low energy"},
    {"track_index": 1, "vibe_name": "Late Night", "grade": "weak", "reason": "..."},
    ...
  ]
}
```

This is the right pattern. [VERIFIED: matches the LLMVibeMappingResponse
precedent in `vibe_clusterer.py:194-206`.] Permissive slim schema, server
resolves to canonical, retry-once on validation failure.

[ASSUMED] **Best-practice corroboration:** Anthropic's own batched
classification examples use the same `{"items": [...]}` envelope pattern,
not parallel calls. The envelope reduces overhead and keeps per-track
context bounded by one shared system prompt. *Source:* training data,
not verified against current Anthropic cookbook this session.
**Mitigation:** the pattern is also the established Composer convention
(Phase 6.1), so it's locked by precedent regardless.

### 3.2 max_tokens for Pass 1 (25 tracks, required reason)

[VERIFIED: math]

Per-track output token budget:
- `track_index`: int — ~3 tokens (JSON encoding)
- `vibe_name`: short string (~5 tokens avg, e.g. "Workout", "Late Night")
- `grade`: one of three literals — ~2 tokens
- `reason`: 5-15 words target → 8-25 tokens conservatively
- JSON overhead per entry: ~10 tokens (brackets, quotes, commas)

Per-track total: ~30-45 tokens. At 25 tracks: **750-1125 tokens**.
Plus envelope (~10 tokens). Plus trailing prose tolerance margin.

CONTEXT.md D-07 says **`max_tokens=3000`** — this is comfortable. Could
be tightened to `2000` and still have margin, but 3000 gives headroom for
long reasons and the JSON-with-prose tolerance the parser handles. Keep
D-07 as locked.

### 3.3 Known failure modes for batched classification with confidence grading

[CITED: well-documented Anthropic best-practice on batched LLM tasks]

1. **Default-to-most-frequent-class on long lists.** LLMs occasionally
   anchor to the modal answer for later entries when the batch is long.
   **Mitigation in CONTEXT.md:** D-01 batch size = 25 (vs 50). Confirmed
   appropriate. [ASSUMED] 25 is below the typical anchor-bias threshold;
   training-data corroborated but not session-verified. Risk if wrong:
   low — D-09 strict-both rubric + Pass 2 peer review independently
   correct anchor bias.

2. **Index drift.** LLM forgets that `track_index: 5` refers to the 6th
   track and re-numbers from 0 in its output. **Mitigation:** require
   `track_index` to echo the input index; server-side validate every
   index is present and in `[0, batch_size)`. The
   `_validate_seed_indices`-style retry pattern from Phase 6.1 covers this.

3. **Over-confident default.** LLMs default to confident answers even
   when uncertain. **Mitigation in CONTEXT.md:** D-10 "uncertainty is
   encouraged" framing. Explicit permission slip is documented as
   high-leverage.

4. **Reason field omission under output pressure.** LLMs drop optional
   fields when output budget is tight. **Mitigation in CONTEXT.md:** D-03
   reason field is REQUIRED, not optional, and the slim schema declares
   it as required (Pydantic raises on missing).

5. **Vibe-name hallucination.** LLM invents a vibe name not in the user's
   list, or mangles casing. **Mitigation:** server-side validate
   `vibe_name in {user_typed_vibes}` (casefold lookup, mirrors Phase 6.1
   WARNING #1); retry-once with corrective prompt on miss.

### 3.4 Retry strategy on per-track validation failure

CONTEXT.md D-06 specifies "Retry-once per batch on validation failure."
**Confirmed correct strategy** — partial-batch retry (retry only the
failed track) is more code complexity for marginal cost savings, and the
batch is already small (25 tracks ≈ ~$0.05/call). Whole-batch retry
matches the Phase 6.1 `_call_llm_with_validation` pattern.

Corrective prompt addendum should be SPECIFIC about what failed:
> "PREVIOUS RESPONSE WAS INVALID: track index 12 had vibe_name='SmoothJazz'
> which is not in your provided vibe list. Valid names: [Workout, Late
> Night, Smooth Jazz, ...]. Re-issue the FULL response with corrected
> vibe names."

Mirrors the existing pattern at `vibe_clusterer.py:1179-1184`. No new
infrastructure.

## 4. Pass 2 Peer-Context Prompt Engineering

### 4.1 Peer context structure: XML > JSON > Markdown

[CITED: Anthropic prompt engineering guide — XML tags for structured input]

Anthropic explicitly recommends XML-tagged sections for structured prompt
input. For ~5000 tokens of peer context across N vibes × 10 peers:

```xml
<vibe_definitions>
  <vibe name="Workout">High-energy synth-heavy tracks for active sessions...</vibe>
  <vibe name="Late Night">Slow, dark, valence-low ambient tracks...</vibe>
  ...
</vibe_definitions>

<peer_tracks>
  <vibe name="Workout">
    <peer>Pumping Pulse — Carpenter Brut (energy=0.92, tempo=128, danceability=0.71, valence=0.45)</peer>
    <peer>...</peer>
  </vibe>
  <vibe name="Late Night">
    <peer>...</peer>
  </vibe>
</peer_tracks>
```

**Why XML over JSON for prompt input:**
- Anthropic's models are trained on XML-tagged prompts.
- Reduces token count vs JSON (no quotes around keys).
- Semantic clarity: a human reading the prompt can parse it.
- The closing tag is a strong signal of section boundaries — reduces
  cross-section bleed.

**Why XML over Markdown:**
- More machine-parseable boundaries.
- No accidental list-bullet ambiguity.

**Caveat:** the peer count and feature vectors are tiny enough that
JSON would also work; the choice is between "good" and "best." If
implementation cost differs (existing helpers emit Markdown), don't
rewrite — pick XML for **new** Pass 2 prompts only.

### 4.2 Do we still need structured response schema when thinking is on?

**Yes.** Thinking is a *reasoning preamble*; the final answer is still a
text block that needs to be parsed. The model can "think through" each
boundary track in the thinking block, then emit a clean JSON answer:

```json
{
  "decisions": [
    {"track_index": 7, "final_vibe_name": "Workout", "reason": "..."},
    {"track_index": 14, "final_vibe_name": "Late Night", "reason": "..."}
  ]
}
```

This is the **right pattern**. Don't try to skip the JSON layer just
because thinking is on. The schema is still our contract for downstream
processing (writing `TrackVibe` rows from a deterministic shape).

Pass 2's slim shape (CONTEXT.md D-33's `LLMVibeBoundaryResponse`)
mirrors Pass 1's — same `model_validate_json` + permissive-slim +
canonical-conversion pattern.

### 4.3 Pass 2 batch size validation

CONTEXT.md D-16: 15 tracks per Pass 2 batch.

Output token math:
- per-track: track_index (~3) + final_vibe_name (~5) + reason (~15) +
  JSON overhead (~10) = ~33 tokens
- 15 tracks × 33 = ~495 answer tokens
- Plus adaptive thinking budget: Claude will use what it needs. For
  boundary-case reasoning across 15 tracks with peer context, expect
  ~1500-3000 thinking tokens per call (15 × ~150 tokens of internal
  per-track deliberation).
- Total output_tokens estimate: ~2000-3500.

**Recommendation:** Pass 2 `max_tokens=4000` (vs Pass 1's 3000). This
leaves comfortable margin for the thinking budget without risking
`stop_reason: "max_tokens"`. [RESEARCH FLAG] The exact thinking budget
adaptive mode allocates for 15-track boundary review is not
deterministic; if measured Pass 2 calls hit `max_tokens` in practice,
raise to 6000-8000. The planner should include a metric/assertion that
logs `stop_reason` per call and flags `max_tokens` truncations.

### 5.2 Cost math validation

CONTEXT.md D-32 estimate: preamble $0.02 + Pass 1 ~$1.20 + Pass 2
~$0.30-0.60 ≈ **$1.50-1.80 per re-cluster**, comfortable under $3 ceiling.

Sanity check at 600 rated tracks:

**Preamble (1 call):**
- Input: ~500 tokens (5 vibe names + framing) × $3/Mtok = $0.0015
- Output: ~500 tokens (5 vibe definitions @ 100 tokens each) × $15/Mtok = $0.0075
- ≈ **$0.01**

CONTEXT.md says $0.02 — slightly conservative, fine.

**Pass 1 (24 batches × 25 tracks):**
- First call writes the cached system prompt (~3000 tokens) at 1h-TTL
  rate: 3000 × $6/Mtok = $0.018 one-time
- Batches 2-24 (23 calls) read the cached prompt: 23 × 3000 × $0.30/Mtok
  = $0.021 total
- Per-batch user prompt (uncached): ~25 tracks × 30 tokens each = 750
  tokens × $3/Mtok = $0.00225 per call × 24 = $0.054
- Per-batch output: ~1000 tokens × $15/Mtok = $0.015 per call × 24 = $0.36
- **Pass 1 total ≈ $0.42**

That's substantially **lower than CONTEXT.md's $1.20 estimate**. The
CONTEXT.md estimate appears to assume larger per-batch input or output
than the conservative numbers above. The math suggests Pass 1 is
comfortably ~$0.40-0.60, not $1.20.

[RESEARCH FLAG] **CONTEXT.md's $1.20 Pass 1 estimate may be 2-3×
conservative.** Recommend the planner not tighten the budget on the
strength of this lower estimate — keep the $3 ceiling, but expect
actual measured cost to come in well under $1.50/re-cluster. The cost
ceiling check via `SELECT SUM(cost_estimate_usd)...purpose LIKE 'vibe_%'`
remains the authoritative measurement.

**Pass 2 (10 batches × 15 tracks, with adaptive thinking):**
- Cached system prompt is the ~5000-token peer context (D-15). One write:
  5000 × $6/Mtok = $0.030 one-time.
- 9 subsequent reads: 9 × 5000 × $0.30/Mtok = $0.0135
- Per-batch user prompt (uncached): ~15 tracks × 80 tokens (denser per
  D-16) = 1200 tokens × $3/Mtok = $0.0036 per call × 10 = $0.036
- Per-batch output (incl. thinking): conservative ~3000 tokens × $15/Mtok
  = $0.045 per call × 10 = $0.45
- **Pass 2 total ≈ $0.52**

CONTEXT.md estimate: $0.30-0.60. The $0.52 figure lands in the upper
half of the range — **consistent**. The adaptive-thinking change vs the
fixed-1024 budget makes little difference here because thinking is bounded
by max_tokens anyway; in practice the model will use a similar effective
budget for the boundary-review task.

**Updated estimate: $0.43 (Pass 1) + $0.52 (Pass 2) + $0.01 (preamble) ≈
$0.96/re-cluster.** Still consistent with CONTEXT.md $1.50-1.80 if Pass 1
batches end up larger than the conservative math; safe under $3 either
way.

### 5.3 Adaptive vs manual thinking cost difference

[CITED: docs]

Adaptive thinking at default `high` effort uses **whatever it needs**,
bounded by `max_tokens`. For boundary-review across 15 tracks, the
effective thinking budget will be similar to a manual 1500-3000 token
allocation. Adaptive will spend slightly more on easier batches
("always think" at `high`) and adapt downward only at `medium`/`low`.

Net effect: adaptive Pass 2 cost ≈ manual Pass 2 cost. The migration is
free in $ terms and forward-compatible with future model versions.

## Common Pitfalls

### Pitfall A: Assuming `response.content[0]` is always the text block

**What goes wrong:** AttributeError on `'ThinkingBlock' object has no
attribute 'text'` the first time Pass 2 runs.
**Why it happens:** Thinking blocks always precede text blocks in
`response.content` per Anthropic's contract.
**How to avoid:** Iterate to find the first block with `type == "text"`.
**Warning signs:** Pass 1 (no thinking) works fine; Pass 2 fails with
AttributeError as soon as thinking is enabled.

### Pitfall B: Using deprecated `{"type": "enabled", "budget_tokens": N}` on Sonnet 4.6

**What goes wrong:** Code starts emitting deprecation warnings; on next
model rotation (Opus 4.7 already, Sonnet 4.7 eventually), the API
returns 400 errors.
**Why it happens:** Anthropic is migrating to adaptive thinking; manual
mode is on a deprecation clock.
**How to avoid:** Use `{"type": "adaptive"}` for D-12.
**Warning signs:** Deprecation warnings in `_log_usage` or
`response.usage` — watch for them on first deploy.

### Pitfall C: Setting `budget_tokens` below 1024 (manual mode only)

**What goes wrong:** 400 error from API.
**Why it happens:** Minimum manual budget is 1024.
**How to avoid:** Not applicable if using adaptive mode. If retaining
manual mode for any reason, enforce `budget_tokens >= 1024` at the
parameter validation layer in `call_with_structured_output`.

### Pitfall D: Streaming JSON parsers (not applicable, but worth flagging)

**What goes wrong:** If a future task switches to streaming, the
JSON-decoder-with-prose-tolerance at `anthropic_client.py:136-147` needs
to accumulate over `text_delta` events instead of one-shot parsing.
**Why it happens:** Streaming emits chunks; the JSON object straddles
chunk boundaries.
**How to avoid:** Out of scope for Phase 6.2 — Composer doesn't stream.
Flag for future readers.

### Pitfall E: `stop_reason: "max_tokens"` truncating Pass 2 answer

**What goes wrong:** Adaptive thinking uses most of `max_tokens` for
the thinking block; answer JSON is truncated mid-emission.
**Why it happens:** `max_tokens` is the total ceiling for thinking +
answer; adaptive can over-allocate.
**How to avoid:** Set Pass 2 `max_tokens=4000` (vs Pass 1's 3000). Log
`response.stop_reason` in `_log_usage` — alert on `"max_tokens"`.
**Warning signs:** Pydantic ValidationError with truncated JSON in the
error message; `stop_reason` field shows `"max_tokens"`.
