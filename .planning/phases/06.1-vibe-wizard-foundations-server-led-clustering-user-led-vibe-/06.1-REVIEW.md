# Phase 06.1: Code Review Report

**Reviewed:** 2026-05-10T00:00:00Z
**Depth:** standard
**Files Reviewed:** 14
**Status:** issues_found

## Summary

Phase 6.1 wires the user-led vibe wizard (textbox-stack input + LLM
name→cluster mapping) and the one-shot DB-wipe migration. The code is generally
well-instrumented (rich docstrings, lazy-import test shims, tight except
clauses, defensive schema tests) but several defects survive review.

The four BLOCKER findings are correctness defects with user-visible impact:

- The Step 3 textbox-stack form serializes its names from `x-data` on submit
  via Alpine's `@submit` handler, but HTMX bypasses the native submit event by
  default, so the hidden `vibe_names` field can be sent with stale/empty JSON
  (BLOCKER 1).
- `_migrate_add_columns` swallows ALL exceptions silently, masking real
  migration failures including the data-mutating `UPDATE track SET energy=...`
  recalc (BLOCKER 2).
- `materialize_clusters` ignores the `merged_from` / `split_from` actions
  contract documented in its own docstring — it uses only `seed_track_indices`,
  never the union of source-vibe members (BLOCKER 3).
- The Phase 6.1 migration deletes `ManagedPlaylist` rows that were just
  successfully archived in Plex without ever calling `archive_playlist` on rows
  whose Plex API call raised an exception, leaving orphaned Plex playlists
  with their composer names intact AND the audit row gone (BLOCKER 4).

Nine WARNING findings cover defensive-coding gaps (no UPDATE rowcount guard,
out-of-range integer source_vibe_ids passing through unchecked, KeyError risk
on tracks_for_prompt indexing, unsafe template silhouette format on None
strings, etc.).

## Blocker Issues

### BLOCKER-01: HTMX submit bypasses Alpine `@submit` serializer, hidden field stays empty

**File:** `app/templates/pages/setup_step3.html:25-48`
**Issue:**
The vibe-names form relies on Alpine's `@submit="serialize()"` handler to copy
the `names` array into the hidden `#vibe-names-hidden` field before submission.
This is incorrect for HTMX-submitted forms. HTMX listens to the form's submit
event but synthesizes its own request from the form's current field values; in
many HTMX configurations the `submit` event listener fires AFTER HTMX has
already serialized the form (or HTMX uses `hx-on::config-request` to intercept
before native `submit`). The result is that the request body contains
`vibe_names=[]` (the initial value at line 48) on the very first submit, OR
a stale value from the previous submit, depending on HTMX version + form-data
extension. The `propose/init` endpoint then trips its "3 to 7" validation and
shows the user a generic error — masking a fundamental wiring bug.

Compounding this: the file does not use HTMX's `hx-include` or the
`htmx:configRequest` event to guarantee the up-to-date `names` array is in the
payload. The 7 partial tests at `tests/test_setup_templates.py` only verify
that the hidden input EXISTS, not that submitted payload matches the typed
names. The integration tests at `tests/test_api_setup.py:213` bypass the
template entirely by POSTing the form-data directly.

**Fix:**
Use Alpine's `@submit.prevent` to take over submission, or — preferred — use
HTMX's `hx-on::config-request` event to inject the serialized value into the
detail at request time:

```html
<form id="vibe-names-form"
      hx-post="/api/setup/propose/init"
      hx-target="#proposal-cards"
      hx-swap="morph:innerHTML"
      x-data="{ names: ['', '', ''], ... }"
      @htmx:config-request="$event.detail.parameters.vibe_names = JSON.stringify(names)"
      class="space-y-3">
  {# no hidden field needed; HTMX gets the value via configRequest #}
</form>
```
Add a behavioral test that submits the rendered form via a headless HTTP
roundtrip and asserts the body received by `/api/setup/propose/init` carries
the user-typed names — not the stale `[]` initial value.

### BLOCKER-02: `_migrate_add_columns` silently swallows ALL exceptions, hiding data corruption

**File:** `app/database.py:199-202`
**Issue:**
`init_db` wraps the entire migration in a bare `except Exception: pass`. This
hides every conceivable failure mode of `_migrate_add_columns`, including:

- The data-mutating `UPDATE track SET energy = ROUND(MIN(MAX(...))) ...`
  recalc at line 155-163. If that UPDATE raises (locked DB, malformed
  expression after a schema drift, etc.) the migration partially completes —
  some `ALTER TABLE` succeeded, the UPDATE didn't — and the app proceeds as
  if nothing happened.
- Any of the `CREATE INDEX` statements raising on a corrupted DB.
- A genuine programming error in the migration helper itself.

The comment "Table may not exist yet on first run — create_all handles it" is
WRONG: `create_all` is called BEFORE `_migrate_add_columns` (line 196), so the
tables always exist by the time the migration runs. The catch-all has no
legitimate trigger condition.

This same anti-pattern would mask a future migration bug indefinitely:
silent corruption with no logged warning.

**Fix:**
Either remove the bare-except entirely (let the migration fail loud at
startup), or catch only the documented expected exception type
(`sqlite3.OperationalError` for the legacy-DB ALTER path at line 135) and
log every other exception:

```python
try:
    _migrate_add_columns(engine)
except sqlite3.OperationalError as exc:
    logging.getLogger(__name__).warning(
        "_migrate_add_columns operational error (likely legacy DB): %s", exc
    )
except Exception:
    logging.getLogger(__name__).exception(
        "_migrate_add_columns failed; aborting startup"
    )
    raise
```

### BLOCKER-03: `materialize_clusters` ignores its own docstring for `merged_from` / `split_from`

**File:** `app/services/vibe_clusterer.py:733-742, 745-841`
**Issue:**
The `materialize_clusters` docstring at lines 750-757 explicitly states:

> - merged_from: union the source vibes' tracks; recompute single centroid.
> - split_from: KMeans(k=2) within the source vibe's tracks.

But the implementation at `_proposal_track_indices_for` (line 733-742) returns
ONLY `proposal.seed_track_indices` regardless of `action`. There is no path
that resolves `source_vibe_ids` → member indices for merged/split actions, and
no inner-k-means call for split. The result:

- `merged_from` proposals: centroid/spread/silhouette are computed only over
  the seed indices (typically 5-15 tracks), not the full union of the two
  source vibes' members. This makes the silhouette score on a "merge two
  vibes" refinement look catastrophically bad (small sample size, narrow
  spread) and misleads the user.
- `split_from` proposals: no actual 2-cluster split is done. Two parallel
  `split_from` proposals each carry their own seed indices, which are server-
  computed from the k-means labels at the cluster level (per `map_user_vibes_to_clusters`),
  but during REFINEMENT (where the LLM emits two `split_from` proposals with
  hand-picked seeds) the centroid math is wrong.

This is silent semantic drift: tests in `test_vibe_clusterer.py` only assert
that `centroid`/`spread`/`silhouette` are populated (line 538-545), not that
they reflect the documented action semantics.

**Fix:**
Either honor the docstring and resolve member indices for each action type:

```python
def _proposal_track_indices_for(prop, ..., source_vibe_members):
    if prop.action in ("merged_from", "split_from", "renamed_from", "keep"):
        members = []
        for sv_id in prop.source_vibe_ids:
            members.extend(source_vibe_members.get(sv_id, []))
        if prop.seed_track_indices:
            members.extend(prop.seed_track_indices)
        return list(set(members))
    return list(prop.seed_track_indices)
```

OR update the docstring to honestly state that ALL actions use only
`seed_track_indices`, and ensure the caller populates them correctly upstream.

### BLOCKER-04: Migration step swallows `archive_playlist` failures THEN deletes the audit row

**File:** `app/main.py:128-167, 170-217`
**Issue:**
The Phase 6.1 migration has two phases. Phase A iterates `ManagedPlaylist`
rows and calls `archive_playlist` best-effort with a tight except clause
(line 152). Phase B (the `_wipe_sync` at line 170) THEN unconditionally
`DELETE FROM ManagedPlaylist` (line 180).

The defect: if `archive_playlist` raises (Plex 401, NAS unreachable,
HTTP timeout — any of the 4 caught types or even something tighter like
`asyncio.TimeoutError` which the tight except will NOT catch), the
ManagedPlaylist DB row is still deleted in Phase B. The Plex playlist
keeps its original `Composer · {name}` title AND its plex_rating_key,
but Composer has lost all audit trail of having owned it. On the next
deploy, the user is presented with stale Composer-titled playlists that
no longer match any DB row — they look "user-renamed" to the dual-marker
check (D-27 / OPS-06).

Worse: if `archive_playlist` is partially-applied (renamed in Plex but
raised before completing the DELETE side), Composer is now in a
half-migrated state with no recovery path.

Additionally, the tight except at line 152 does NOT catch
`asyncio.TimeoutError`, `ConnectionRefusedError`, `OSError`,
`asyncio.CancelledError`, or any subprocess-related errors that could
occur if the Plex API uses subprocess delegation. Those will bubble up
and abort the migration mid-loop, leaving some playlists archived and
the rest in legacy state — but worse, the gate marker is NOT YET written
(that happens in `_wipe_sync`), so on next restart the WHOLE migration
re-runs and tries to re-archive playlists that no longer have managed
rows pointing to them.

**Fix:**
Either:
1. Track which `ManagedPlaylist` rows successfully archived and only DELETE
   those, leaving failures in place for the user to inspect/retry:
   ```python
   archived_ids: set[int] = set()
   for mp in managed:
       try:
           await _pps.archive_playlist(...)
           archived_ids.add(mp.id)
       except (...): ...
   # In _wipe_sync, only delete rows whose id is in archived_ids,
   # leaving unarchived rows + their composer_name visible for retry.
   ```
2. Widen the except clause to include `asyncio.TimeoutError`,
   `ConnectionError`, `OSError`, `Exception` (with explicit log) and
   ensure the migration is fully idempotent if it partially completes.
3. Write the gate marker (Step 2 already does — confirm it's NOT
   overwritten by the wipe) BEFORE Step 3 so the migration never re-runs,
   accepting some Plex orphans on partial failure but in exchange
   guaranteeing convergence.

The current behavior gives the worst of all worlds: orphan playlists in
Plex AND a partially-applied migration that may or may not re-run.

### WARNING-01: `_resolve_source_vibe_ids` integer path bypasses range validation

**File:** `app/services/vibe_clusterer.py:681-683`
**Issue:**
The function appends every integer from `llm_ids` to `resolved` verbatim
without checking that the integer is in `[0, len(prior_proposals.proposals))`.
If the LLM hallucinates `source_vibe_ids: [42]` against a 3-proposal prior
set, the canonical `VibeProposal` validates fine (`List[int]`) but downstream
consumers like `api_vibes.recluster_commit` look up the source vibe by id
and crash or skip silently. The docstring at line 663-672 says strings
without a name match are dropped with a warning — integers without a valid
range index deserve the same treatment.

**Fix:**
```python
for entry in llm_ids:
    if isinstance(entry, int):
        if prior_proposals is None or 0 <= entry < len(prior_proposals.proposals):
            resolved.append(entry)
        else:
            logger.warning(
                "vibe_clusterer: LLM source_vibe_ids contained out-of-range "
                "integer %d (valid: 0..%d); dropping",
                entry, len(prior_proposals.proposals) - 1 if prior_proposals else -1,
            )
        continue
    ...
```

### WARNING-02: `tracks_for_prompt[mi]` KeyError if cluster member index outside prompt range

**File:** `app/services/vibe_clusterer.py:1082-1097, 1192-1199`
**Issue:**
Lines 1082, 1091, 1113, 1193 use `tracks_for_prompt[mi]` where `mi` is a
k-means label index. The k-means is fitted on `feature_matrix` which has
exactly `n_rated` rows == `len(tracks_for_prompt)`. If `_aggregate_rated_set_sync`

filtered post-construction), this becomes an `IndexError` instead of a

A static `assert len(feature_matrix) == len(tracks_for_prompt) == len(index_map)`
at the top of `map_user_vibes_to_clusters` would surface this immediately
rather than crashing inside a list comprehension.

**Fix:** add the length-equality assertion at line 1026 (after the cold-start
gate). Defensive but cheap.

### WARNING-03: `silhouette` format spec assumes float, fails on stringified None

**File:** `app/templates/partials/vibe_proposal_card.html:60`
**Issue:**
```jinja
silhouette {{ "%.2f"|format(proposal.silhouette or 0) }}
```
If `proposal.silhouette` is `None`, `(None or 0)` returns `0` → formats fine.
But if `materialize_clusters` ever sets `proposal.silhouette = "0.0"` (string,
not float — easy regression because the field type is `Optional[float]` but
Pydantic accepts coercion at validation but not always at dump-load), the
format spec will raise `TypeError: must be real number`. This is a brittle
"works because Pydantic happens to keep it numeric" coupling.

**Fix:**
```jinja
silhouette {{ "%.2f"|format(proposal.silhouette|default(0)|float) }}
```
The `|float` filter coerces and defaults to 0 on TypeError.

### WARNING-04: `finalize` re-entrancy guard doesn't reset on uncaught exception

**File:** `app/routers/api_setup.py:447-457, 459-470`
**Issue:**
`_finalize_status` is set to `state="running"` at line 517, then transitions
to "completed" or "failed" at lines 654 / 664. There is no `try/finally`
wrapping the whole `for` loop, so if an unexpected exception escapes the
inner `try` (e.g., the `state.step != "confirming"` branch at line 661 raises
because session is closed), the status stays stuck on "running" forever.
The HTMX poll endpoint at `/api/setup/finalize/status` will return the
running banner indefinitely, and the user has no way to recover except to
restart the container (which resets the module global).

**Fix:** wrap with `try/finally`:
```python
_finalize_status = FinalizeStatus(state="running", ...)
try:
    for prop in targets:
        ...
finally:
    if _finalize_status.state == "running":
        _finalize_status = FinalizeStatus(
            state="failed", created=created_count, total=total,
            last_error="Unexpected error during finalize",
        )
```

### WARNING-05: `propose_init` last_llm_call_id lookup happens BEFORE the LLM call's row is committed

**File:** `app/routers/api_setup.py:336-340`
**Issue:**
`map_user_vibes_to_clusters` at line 307 calls the Anthropic client which
should insert an `LLMUsage` row inside the call (per the Phase 5
AnthropicClient v2 invariant). But `_latest_llm_call_id` at line 336 reads
from the same `session` that was passed to `propose_init` — not a fresh
session. SQLAlchemy session caching may serve a stale view that doesn't see
the newly-inserted `LLMUsage` row written by a DIFFERENT session inside
`call_with_structured_output`.

The test at `tests/test_api_setup.py:267-277` works around this by manually
inserting an `LLMUsage` row BEFORE the propose call. The production path will
silently set `last_llm_call_id = None` (or worse, an unrelated older id) on
every first wizard run.

**Fix:** add `session.expire_all()` or `session.commit()` before
`_latest_llm_call_id`:
```python
session.commit()  # flush any pending writes; refresh view
state.last_llm_call_id = _latest_llm_call_id(session, "vibe_clustering_")
```

### WARNING-06: `_pick_best_k` produces `k_max < 3` silently floors to 3 — wastes LLM calls

**File:** `app/services/vibe_clusterer.py:339-343`
**Issue:**
The comment says "Defensive: shouldn't reach here because the cold-start gate
fires earlier, but keep a safety floor." But `n_rated // 15 < 3` means
`n_rated < 45`. The cold-start gate at line 868 only fires below 30, so
n_rated in [30, 45) reaches this code with `k_max < 3`. The code silently
forces `k_max = 3`, which means `_pick_best_k` runs k-means with k=3 on a
44-track dataset (~14 tracks per cluster — well below the silhouette-
viability floor). The resulting silhouette will be poor, the LLM still gets
called, and the user sees a confused result.

Either bump the cold-start floor to 45, or short-circuit `_pick_best_k` to
return `degraded_mode=True` when `k_max < 3`.

**Fix:**
```python
if k_max < 3:
    # Tiny library — fall back to k=3 but mark degraded.
    k = 3
    km = KMeans(n_clusters=3, n_init="auto", random_state=42).fit(X_normalized)
    sil = float(silhouette_score(X_normalized, km.labels_))
    return 3, km.labels_, km.cluster_centers_, sil, True  # always degraded
```

### WARNING-07: `materialize_clusters` silhouette fallback hides real errors

**File:** `app/services/vibe_clusterer.py:833-839`
**Issue:**
```python
try:
    prop.silhouette = float(silhouette_score(X_norm, labels))
except Exception:
    prop.silhouette = 0.0
```
Bare `except Exception: prop.silhouette = 0.0` masks every sklearn error
(invalid label distribution, NaN in matrix, OOM on large matrices) and
serves a misleading `0.0` to the LLM + UI. A track set with `silhouette=0.0`
looks like a useless cluster; the user has no way to distinguish "the math
gave 0" from "the math raised an exception".

**Fix:** narrow to `ValueError` (the only documented `silhouette_score`
exception for degenerate label distributions) and log the others:
```python
try:
    prop.silhouette = float(silhouette_score(X_norm, labels))
except ValueError:
    prop.silhouette = 0.0
except Exception:
    logger.exception("Unexpected silhouette_score failure on proposal %r", prop.name)
    prop.silhouette = None  # signal "unknown" not "bad"
```

### WARNING-08: `_aggregate_rated_set_sync` top_artists/genres counts include incomplete-feature rows

**File:** `app/services/vibe_clusterer.py:288-301`
**Issue:**
The code at line 288-301 builds `artist_counts` and `genre_counts` from
`all_tracks` (the full rated set BEFORE feature-completeness filter at line
250-257). So a user with 100 rated tracks, only 30 of which have Essentia
analysis complete, gets `top_artists` reflecting the FULL 100 — including
artists whose tracks the LLM cannot map to a cluster. The LLM prompt at line
394-396 then advertises "Top 10 artists by rated count" with counts that
don't match `rated_track_count` (which is the filtered set per line 303).

This is a subtle but real bug: the LLM's clustering prompt has inconsistent
"top artists" vs "rated track count", and may name a vibe after an artist
that's actually absent from the feature matrix.

**Fix:** build the counters from `tracks_for_prompt` (the filtered set):
```python
artist_counts = Counter(t["artist"] for t in tracks_for_prompt if t.get("artist"))
all_genres = []
for t in tracks_for_prompt:
    if t.get("genre"):
        all_genres.extend(g.strip() for g in t["genre"].split(",") if g.strip())
genre_counts = Counter(all_genres)
```

### WARNING-09: `archive_playlist` migration TIGHT except misses Asyncio errors

**File:** `app/main.py:152-157`
**Issue:**
The tight except catches `(plexapi.exceptions.PlexApiException,
httpx.HTTPError, PermissionError, TypeError)`. This explicitly excludes:

- `asyncio.TimeoutError` (raised on Plex API timeout — common on slow NAS)
- `ConnectionError` / `ConnectionRefusedError` (Plex container down)
- `OSError` (network unreachable on first boot when Plex isn't up yet)
- `KeyError` / `AttributeError` (Plex API response shape drift)

Any of these will abort the migration loop mid-iteration. Because the gate
marker is only written by `_wipe_sync` AFTER the loop completes, on next
restart the migration re-runs from scratch and re-attempts archiving
already-archived playlists (creating `Composer · X (archived) (archived)`
naming pollution).

The plan-comment at line 158-162 is incorrect: `TypeError` is caught here
mainly to surface signature drift, but the broader Plex-failure surface
is not covered. Either widen the except OR move the gate-marker write to
fire defensively after each successful archive.

**Fix:** widen the except to include the Plex API surface that's actually
observed in production:
```python
except (
    plexapi.exceptions.PlexApiException,
    httpx.HTTPError,
    asyncio.TimeoutError,
    ConnectionError,
    OSError,
    PermissionError,
    TypeError,
    AttributeError,
    KeyError,
):
```
