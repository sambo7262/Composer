# Phase 6.1: Vibe Wizard Foundations: server-led clustering + user-led vibe input - Context

**Gathered:** 2026-05-10
**Status:** Ready for planning

<domain>
## Phase Boundary

Phase 6.1 fixes three foundational gaps that Phase 6 UAT surfaced before any later phase can build on the vibe pipeline:

1. **Server-led membership.** Phase 6's clusterer runs k-means and gets real cluster labels for every rated track, but never uses them — it asks the LLM to pick `seed_track_indices` per proposal, and Claude returns sparse 5–10 picks per vibe. Result: a 600-track library produces 7 playlists with ~10 tracks each. 6.1 backfills `seed_track_indices` server-side from the k-means labels so EVERY rated track lands in its nearest vibe (plus optional 2nd vibe per soft-membership margin). The LLM is demoted from "member picker" to "namer/describer/refiner."

2. **User-led vibe input.** Phase 6 Step 3 starts with an LLM proposal call (Claude invents 3–7 vibe names + descriptions). User testing showed this wastes compute and removes control — the user already knows what playlists they want ("workout, focus, late night drive, synth heavy"). 6.1 replaces Step 3's opening with a textbox: user types 3–7 vibe names, server runs k-means with k = user-typed count, then ONE LLM call maps each cluster centroid → the best-matching user name with a structured `fit: strong | weak | no_match` grade. The conversational refinement loop (merge/split/rename/drop/add) stays intact post-mapping.

3. **Track listing for verification.** Phase 6 cards rendered seed_track_indices verbatim — when the LLM returned empty arrays, expanded "Song list" disclosures showed nothing. With server-led membership, every card has real members. 6.1 keeps the D-11 pattern (5 closest-to-centroid seed tracks + "Show all N" Alpine x-collapse disclosure) but with REAL data, and adds the fit-grade chip per card so the user sees "✓ strong fit · 85 tracks" before committing.

Phase 6.1 does NOT add new requirements (VIBE/WIZ/DEBUG IDs unchanged), does NOT change the slot-in hot path (`vibe_service.slot_track` semantics carry forward), and does NOT touch the re-cluster commit path (D-21 from Phase 6 is correct as-is — the broken part was initial proposal, not re-cluster reconciliation). It is a targeted refactor of the initial-proposal flow + Step 3 UI + an existing-state wipe on first deploy.

</domain>

<decisions>
## Implementation Decisions

### Server-led clustering algorithm

- **D-NEW-01: Hybrid mapping with fit grading.** Step 3 flow:
  1. User types N vibe names (3 ≤ N ≤ 7).
  2. Server runs k-means with `k = N` (overrides Phase 6's silhouette auto-k for this path). Constraints: still requires `n_rated >= 30`. Below 30 → cold-start gate; 30–49 → degraded single-vibe mode forces N=1 (override user input with explanation).
  3. ONE LLM call (`purpose="vibe_clustering_user_led"`) sends: (a) the N user-typed names; (b) each of the N cluster centroids (z-score-normalized 4-D features) + top artists/genres in that cluster + top 10 closest-to-centroid tracks; (c) the cached taste-profile prefix (Phase 6 D-35 / 1h TTL).
  4. LLM returns a permutation mapping `[user_name → cluster_index]` plus, per name, a `description` (1 line) and a `fit` enum (`strong | weak | no_match`). If `no_match`, LLM also emits a `reason` string explaining why no cluster matches that name.
  5. Server materializes `VibeProposalSet` from the mapping: each proposal's `seed_track_indices` comes from the k-means labels for that cluster (server-side, never the LLM). The fit grade flows through to the wizard card UI.
  6. Step 4 review surfaces fit grades inline. User can drop weak-fit or no-match vibes before "Push to Plex" — but is never forced to. A `no_match` vibe with 0 members is allowed to commit (empty Plex playlist with a name — clarifies the user's intent for future ratings).

- **D-NEW-02: Conversational refinement loop preserved.** After D-NEW-01 produces the initial mapped proposal set, the existing Phase 6 refinement loop (D-01, D-02, D-04, D-05) runs unchanged. User can type natural-language commands ("merge focus + late night", "split workout into cardio and lifting", "add a sunday morning vibe"). Each turn calls `vibe_clusterer.refine_proposals` with `purpose="vibe_clustering_refine"`. The CRITICAL change: post-refinement membership for each proposal is server-recomputed via the existing constrained-k-means logic (Phase 6 D-05), NEVER the LLM's `seed_track_indices`. The LLM may still return `seed_track_indices` (for new vibes via `action="new"`) as a HINT for cluster initialization, but server-side k-means always produces the final members.

- **D-NEW-03: Soft-membership margin lands here.** Phase 6's D-15 specifies soft membership (track joins a second vibe if distance to that centroid ≤ closest_distance + 1·std-dev, capped at 2 vibes per track). This logic exists in `vibe_service.slot_track` already but in Phase 6 it never matters for initial population (because seed_track_indices was sparse → most tracks never got assigned anywhere). With server-led membership in 6.1, soft margin runs for real on the initial slot-in pass. Tracks meeting the margin land in 2 `TrackVibe` rows. Verified observable: a 600-track library should average 1.0–1.4 vibes per track post-initial-slot-in.

### Vibe count & range constraints

- **D-NEW-04:** Vibe count = 3 to 7 (preserves Phase 6 k_max formula `min(7, n_rated // 15)`). Reject `< 3` or `> 7` user input with inline error before clustering. Cold-start gate `<30 rated` and degraded `30–49 rated` paths carry forward from Phase 6 D-10 unchanged (degraded mode forces N=1).

- **D-NEW-05:** Refinement turn cap = 10 per session (Phase 6 D-04 carries forward). Daily 50-call LLM circuit breaker still applies.

### Step 3 UI — user-led input

- **D-NEW-06:** Step 3 opens with a textbox-stack input: three text fields by default, "+ Add another" button to add up to 7. Each input has placeholder text rotating through examples ("workout", "focus", "late night drive", "synth heavy"). Below the inputs: small helper "Type names of playlists you want — Composer will match tracks." Bottom CTA: "Cluster my library" (becomes "Clustering... ~5s" during the LLM call).

- **D-NEW-07:** Inline validation on Cluster CTA:
  - Reject blank entries (trim whitespace, ignore empties — recount).
  - Reject duplicates (case-insensitive trim).
  - Reject `< 3` or `> 7` names with inline error.
  - Names sanitized for the eventual Plex playlist title (`Composer · {name}`) — reject characters Plex rejects (currently: not aware of any Plex restrictions on playlist names; treat as "trim only" until proven otherwise).

- **D-NEW-08:** Vibe-name display in cards (Step 3 results + Step 4 review):
  - Name (editable inline, click-to-edit pattern carries forward)
  - Description (LLM-generated, editable inline)
  - Audio-feature chip from `feature_chip_text(centroid)` (Phase 6 D-11)
  - Fit grade chip: ✓ strong fit · 85 tracks, ⚠ weak fit · 34 tracks, ✗ no match · 0 tracks (with LLM's reason on hover/tap)
  - 5 closest-to-centroid seed tracks shown as "Title — Artist"
  - "Show all N tracks" disclosure — default-collapsed, Alpine x-collapse expands inline, scrollable, no pagination cap (Phase 6 D-11 pattern verbatim, just with real data)
  - Silhouette score (small secondary text)

### Existing-state migration

- **D-NEW-09: Wipe + re-run on first deploy.** Phase 6.1's startup migration step (in `lifespan`, runs once per container start, idempotent):
  1. Check for `Composer · ` Plex playlists registered in `ManagedPlaylist`. If any exist, rename each in Plex to `Composer · {name} (archived)` via `plex_playlist_service.archive_playlist` (4-arg signature: plex_url, plex_token, plex_rating_key, current_name). Plan 02 execution amended this from the originally-specified "(legacy)" to "(archived)" — the existing `archive_playlist` helper already renames to "(archived)" and deletes the ManagedPlaylist row in one shot. Adopting the existing helper avoided introducing a separate rename_playlist + DELETE flow.
  2. Delete all rows from `Vibe`, `TrackVibe`, `ManagedPlaylist`, `SlotInLog`. Truncate `SetupState` (reset to `step="rating_source"`, all draft state cleared).
  3. Clear all `Track.pending_slot_in` flags (no slot-in is pending anymore — the rated set will be re-evaluated when the new wizard completes).
  4. Log the migration count to `event_handlers` log: "Phase 6.1 migration: archived N Plex playlists, cleared M vibes, K trackvibes."
  5. After this migration, `GET /` redirects to `/setup` per Phase 6 D-07 (Vibe.count() == 0 AND rated_count >= 1 → wizard).
  
  Migration runs ONCE — gated by a one-row marker table `MigrationLog(phase_id='6.1', completed_at=NULL/timestamp)` (or by checking `not ManagedPlaylist.exists() AND Vibe.count() == 0 AND not legacy-playlists-in-Plex` to detect "already migrated" state). The exact gate mechanism is Claude's discretion; the constraint is "runs zero times if already migrated, exactly once otherwise."

### LLM call architecture

- **D-NEW-10:** New `purpose` value: `"vibe_clustering_user_led"` for the D-NEW-01 mapping call. Existing values (`vibe_clustering_initial`, `vibe_clustering_refine`, `vibe_clustering_recluster`) carry forward — the user-led path replaces `vibe_clustering_initial` in the wizard's initial-proposal slot (the old `vibe_clustering_initial` path is removed since user-led mode is the only Step 3 path going forward).

- **D-NEW-11:** Pydantic schema for the user-led mapping response — new `LLMVibeMappingResponse` (sibling to `LLMVibeProposal` from the recent hotfix):
  ```python
  class LLMVibeFit(BaseModel):
      user_name: str             # echoed back from input
      cluster_index: int         # 0..N-1 — which k-means cluster
      description: str           # 1-line vibe description
      fit: Literal["strong", "weak", "no_match"]
      reason: Optional[str]      # required when fit == "no_match"
  
  class LLMVibeMappingResponse(BaseModel):
      mappings: List[LLMVibeFit]  # length == N user names; cluster_index must be permutation of [0..N-1]
  ```
  Server validates: (a) mappings length matches user-input count; (b) cluster_index set is a permutation (no duplicates, all in range); (c) every `fit="no_match"` has a non-empty reason. On validation failure: retry once with corrective prompt (mirrors Phase 6 D-03 / `_validate_seed_indices` retry pattern). Second failure: surface refine_error partial; user is offered "try again" or "remove this name."

### Claude's Discretion

- Exact placeholder rotation order and the helper-text wording for the Step 3 textbox UI (per D-NEW-06).
- The visual treatment of the fit-grade chip (color coding, icon choice). Should follow the existing UI-SPEC.md design tokens.
- Migration gate mechanism (D-NEW-09): one-row marker table vs. state-detection heuristic. Pick whichever is simpler to test idempotency on.
- The exact set of `Track` table queries during the migration cleanup (D-NEW-09 step 3) — whether to bulk-update or row-by-row.
- Specific Tailwind classes for the textbox-stack layout (per Phase 6 mobile-first conventions).
- Whether the "+ Add another" button is disabled at 7 inputs or just no-ops; UX detail.
- Whether `no_match` vibes are silently allowed to commit at Step 4, or require an explicit "Yes, push empty playlist" confirmation. Default: allow silently.
- Whether to surface the fit grade in `/debug/vibes` (likely yes — adds diagnostic value, doesn't cost anything).

<specifics>
## Specific Ideas

- **The user's exact vision: "let me input the vibe rather than a guess."** Phase 6.1's Step 3 IS that path — the user types names first, server clusters around them. No "Suggest some for me" alternative path (the user rejected the hybrid choice during discussion).

- **"Make sure tracks are listed to help verification."** Two-pronged: (1) cards now have REAL members from server-led k-means → expanding "Show all N tracks" surfaces actual data; (2) the fit-grade chip surfaces per-card confidence so the user can spot a problematic vibe BEFORE finalize.

- **"More tracks per playlist."** Direct consequence of server-led k-means. A 600-track library divided among 7 vibes averages ~85 tracks per vibe (pure cluster membership) + some tracks join a 2nd vibe via soft margin → expect 100–140 tracks per Plex playlist. Plexamp performance is fine at that scale (tested elsewhere in v1.0).

- **"Core functionality that gets built on."** Phase 7 (Suggestions Queue) reads from vibe centroids + member counts to seed the Suggestions ranking shortlist. Phase 8 (Lidarr Discovery) uses the vibe centroids to find similar artists. Both inherit from Phase 6.1's correct member population — neither will work right until 6.1 lands.

- **"Synth heavy is genre-driven, not just feature-driven."** The Hybrid mapping (D-NEW-01) gets each cluster's TOP ARTISTS + GENRES in the LLM prompt — not just the audio centroid. This is why "synth heavy" can map correctly even though synthwave and synth-pop have very different tempo/energy: the artist/genre context disambiguates. The fit grade will be ⚠ weak if the user's library has synth artists scattered across multiple clusters.
