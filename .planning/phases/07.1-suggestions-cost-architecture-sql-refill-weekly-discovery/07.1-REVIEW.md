## Summary

The phase-07.1 implementation does the right things in the load-bearing
places. SQL refill correctly filters `Vibe.is_active=True` in both
`_read_vibe_pool_weights_sync` AND `_read_top_n_for_vibe_sync`
(Blocker #7 satisfied — verified end-to-end by
`test_create_then_archive_vibe_excludes_subsequent_picks`).
`MaxTokensTruncationError` is raised on `response.stop_reason == 'max_tokens'`
with the LLMUsage row logged BEFORE the raise so cost telemetry stays
accurate (verified by `test_raises_on_stop_reason_max_tokens`).
`discovery_call_weekly`'s retry surface is correctly bounded to the
truncation signal (verified by three retry tests). The startup catch-up
gate sits OUTSIDE the outer `with Session(...)` in `start_scheduler`
(W9 — verified by `test_catch_up_gate_does_not_open_nested_session`).
Phase 5 conventions (D-08 singletons, D-09 `_*_sync` invariant,
to_thread wrapping) are enforced by AST tests in
`test_suggestions_service.py` and `test_suggestions_discovery.py`.

The four warnings below are real correctness defects that bite in
specific but realistic edge cases (a position-collision when the mirror
has been drained down to exactly the row at position 0; misleading dead
code that imports non-existent env vars; over-broad exception swallowing
that papers over a missing Anthropic configuration in production with a
401 round-trip instead of a clean skip; SQL `LIKE` wildcard collision).
None of them block ship, but all of them should be fixed before they
become harder-to-debug field reports.

## Warnings

### WR-01: Position-collision when mirror has been drained down to position=0

**File:** `app/services/suggestions_service.py:682-685`
**Issue:** `_write_sql_refill_results_sync` computes the next mirror
position as:

```python
max_pos = session.execute(
    text("SELECT COALESCE(MAX(position), -1) FROM suggestionsmirror")
).first()
next_pos = int((max_pos[0] if max_pos else -1) or -1) + 1
```

The `or -1` short-circuits on any falsy value, including `0`. So when
the highest existing position is exactly `0` (e.g., the user has played
every other suggestion and only position 0 remains), `(0 or -1)` evaluates
to `-1` and `next_pos` becomes `0`. The new pick is then inserted at
position 0, colliding with the existing row.

`SuggestionsMirror` has `UNIQUE(track_id)` but NOT `UNIQUE(position)`, so
no IntegrityError surfaces — the queue silently ends up with two rows at
position 0. The `/suggestions` page orders by `position ASC`, which means
the new row sorts together with the survivor in undefined order.

The identical defect exists in `app/services/suggestions_discovery.py:481`
(`_write_discovery_picks_sync`).

**Fix:**

```python
max_pos = session.execute(
    text("SELECT COALESCE(MAX(position), -1) FROM suggestionsmirror")
).first()
# Use the column value directly; COALESCE already handles the no-rows
# case. The previous `or -1` short-circuits on the legitimate value 0.
raw = max_pos[0] if max_pos is not None else -1
next_pos = (int(raw) if raw is not None else -1) + 1
```

Apply the same fix in `_write_discovery_picks_sync`.

### WR-02: `fresh_db` fixture sets a meaningless env var; the actual DB path comes from `tmp_data_dir`

**File:** `tests/conftest.py:121-141`
**Issue:** The `fresh_db` fixture body reads:

```python
db_path = tmp_path / "test.db"
monkeypatch.setenv("COMPOSER_DB_PATH", str(db_path))
db_module._engine = None
init_db()
```

But `app/config.py` does NOT consume `COMPOSER_DB_PATH`. The recognized
env var is `COMPOSER_DATA_DIR`:

```python
DATA_DIR = os.environ.get("COMPOSER_DATA_DIR", os.environ.get("_COMPOSER_LOCAL_DEV", "./data"))
DATABASE_URL = f"sqlite:///{DATA_DIR}/composer.db"
```

The `monkeypatch.setenv` line and the `db_path = tmp_path / "test.db"`
local are dead — they have no effect. The actual database used by the
fixture is `tmp_path/composer.db`, set by the autouse `tmp_data_dir`
fixture that overrides `config.DATABASE_URL` directly. The fixture still
works (by accident, via the autouse override), but the docstring's claim
that `fresh_db` "overrides COMPOSER_DB_PATH" is false. A future change
to `tmp_data_dir` (e.g., removing the autouse override) would silently
break every `fresh_db` test.

**Fix:** Either (a) drop the misleading `monkeypatch.setenv` and `db_path`
locals and document that `fresh_db` relies on `tmp_data_dir` for its
fresh DB, or (b) make the fixture actually own its DB path independently
of `tmp_data_dir`:

```python
@pytest.fixture
def fresh_db(tmp_data_dir, monkeypatch):
    """Phase 5 lazy-engine pattern — fresh SQLite per test.

    Relies on the autouse ``tmp_data_dir`` fixture which has already
    overridden ``config.DATABASE_URL`` to point at ``tmp_path/composer.db``.
    This fixture additionally resets the engine singleton and runs
    ``init_db()`` so every consumer gets the FULL ``_migrate_add_columns``
    schema (LLMUsage.error_text, DiscoveryState, etc.).
    """
    from app import database as db_module
    from app.database import get_engine, init_db

    db_module._engine = None
    init_db()
    engine = get_engine()
    with Session(engine) as session:
        yield session
    db_module._engine = None
```

### WR-03: `discovery_call_weekly` silently substitutes `"test-key"` when Anthropic credentials are missing

**File:** `app/services/suggestions_discovery.py:667-676`
**Issue:** The discovery cron reads credentials inside a broad
`except Exception` that papers over every failure with a hard-coded test
key:

```python
try:
    api_key, model = await asyncio.to_thread(
        _read_anthropic_credentials_sync
    )
except Exception:
    # Tests monkeypatch ``AnthropicClient`` itself, so missing
    # credentials in unit tests is expected — fall through with
    # placeholders. The fake constructor will discard them.
    api_key, model = ("test-key", "claude-sonnet-4-6")
client = AnthropicClient(api_key, model)
```

In production this means: if Anthropic is not configured at the time the
weekly cron fires, the cron instantiates `AnthropicClient("test-key", ...)`
and proceeds to call the live API. The API returns 401, which surfaces
as a generic `Exception` inside the retry loop, which writes
`LLMUsage(purpose="discovery_weekly_error", error_text="AuthenticationError: ...")`.
The user has to dig into `/debug/suggestions` to discover their key
isn't set. Worse, every failed call still counts toward
`DAILY_QUOTA=50` via the breaker's aggregate SELECT
(`_aggregate_counters_sync` counts rows whose purpose `LIKE 'discovery_%'`
regardless of cost).

The plain-language fix: when Anthropic isn't configured, the cron should
skip cleanly with `LLMUsage(purpose="discovery_weekly_skipped_no_credentials", ...)`
and `state="idle"` — mirroring the existing `skipped_no_candidates` /
`skipped_no_taste_profile` paths. Tests already monkeypatch
`AnthropicClient` at the module attribute layer (see
`_make_fake_anthropic_client`), so they don't need the placeholder
fallback at all.

**Fix:**

```python
try:
    api_key, model = await asyncio.to_thread(
        _read_anthropic_credentials_sync
    )
except ValueError as exc:
    logger.warning(
        "discovery_call_weekly: Anthropic not configured (%s); skipping",
        exc,
    )
    await asyncio.to_thread(
        _log_discovery_failure_sync,
        "skipped_no_credentials",
        str(exc)[:200],
    )
    _status = DiscoveryServiceStatus(
        state="idle",
        last_run_at=_status.last_run_at,
        last_error=str(exc)[:200],
        last_picks_made=0,
        last_increment_at=_status.last_increment_at,
    )
    return
client = AnthropicClient(api_key, model)
```

If you genuinely need the test-injection path, plumb that through an
explicit "test mode" parameter or factory hook rather than a broad
exception swallow.

### WR-04: `_get_anthropic_client()` lacks the `_sync` suffix yet opens a Session — violates the AST invariant by spirit

**File:** `app/services/suggestions_service.py:524-529`
**Issue:** The shim:

```python
def _get_anthropic_client():
    """Async-friendly wrapper that runs the sync constructor in a worker
    thread (Phase 5 D-09). Tests can monkeypatch THIS attribute to inject a
    mock client without going through the settings table.
    """
    return _get_anthropic_client_sync()
```

The docstring claims it runs the sync constructor "in a worker thread",
but the body simply calls `_get_anthropic_client_sync()` synchronously —
no `asyncio.to_thread`, no `await`. It would block the event loop if
called from any `async def`.

The function is currently unreferenced (Phase 7.1 D-D1 deleted the only
caller). The AST test `TestSuggestionsServiceAstShape` does NOT trip on
it because `_get_anthropic_client_sync` IS suffixed `_sync` — it's the
shim wrapper that opens the Session at one remove that's misleading.

Two correctness risks for future maintainers:
1. The docstring's "in a worker thread" claim is false; someone reading
   this expects it to be safe to `await` (it isn't — it's not even
   async).
2. The name lacks the `_sync` suffix, so the next AST test author might
   not flag a future caller that awaits it.

**Fix:** Either delete the shim entirely (it has no callers) or rename
it and align the body with the docstring:

```python
async def _get_anthropic_client():
    """Async-friendly wrapper that runs the sync constructor in a worker
    thread (Phase 5 D-09). Tests can monkeypatch THIS attribute to inject a
    mock client without going through the settings table.
    """
    return await asyncio.to_thread(_get_anthropic_client_sync)
```

Recommendation: delete it. Phase 7.1 D-D1 already states there is no
LLM call site in `suggestions_service` anymore, and tests that need to
inject a mock can monkeypatch `_get_anthropic_client_sync` directly.

## Info

### IN-01: SQL `LIKE` wildcard collision risk in cost-breaker and discovery purpose prefixes

**File:** `app/services/llm_cost_breaker.py:100`, `app/services/suggestions_discovery.py:637`
**Issue:** `purpose LIKE 'discovery_%'` and `purpose LIKE 'suggestions_%'`
both treat the underscore as a single-character SQL wildcard. So
`purpose='discoveryX...'` or `purpose='suggestionsXfoo'` would also match.
There are no purposes today that exercise this, but a future label like
`discoveryless` or `suggestions42` would silently get counted toward the
wrong breaker prefix. Low impact at current usage but a latent footgun.

**Fix:** Escape the `_` literal with `LIKE 'discovery\_%' ESCAPE '\\'`,
or pre-filter the in-memory rows by `startswith()` and accept the
ergonomic regression.

### IN-02: Pages.py routes are `async def` but call `session.exec(...)` synchronously

**File:** `app/routers/pages.py:35-66, 84-122, 125-159, 281-392, et al.`
**Issue:** Every route in `pages.py` is `async def` but uses
`session: Session = Depends(get_session)` and reads via `session.exec(...).all()`
directly — no `asyncio.to_thread`. Strictly, this violates Phase 5 D-09
(no blocking I/O in async). In practice it's the project-wide pattern
for HTML page routes and predates Phase 7.1; flagging once for the
record. The Phase 7.1 additions in `read_settings` (LLMUsage rolling-window
SELECT, breaker state computation) follow this same shape — they don't
make things worse, they just inherit the existing convention.

**Fix (deferred / project-level):** If you want to clean this up, the
canonical fix is to move the DB queries into `_*_sync` helpers and
dispatch via `asyncio.to_thread`. Out of scope for Phase 7.1; mentioning
so it lands on the future-cleanup pile.

### IN-03: N+1 queries on the `/suggestions` and `/debug/suggestions` page renders

**File:** `app/routers/pages.py:144-154, 235-243`
**Issue:** Both `read_suggestions` and `read_debug_suggestions` loop the
mirror rows and fire one `select(Track)` and one `select(Vibe)` per row.
For a 30-row mirror that's 60 extra queries. The `/debug/vibes` page
already paid down this same N+1 (`IN-06` fix in pages.py — batch-hydrate
via `WHERE id IN (...)`). The same pattern would slot in cleanly here.

Performance is out of scope for v1 per the review charter, but this is
a near-zero-cost refactor that the codebase already has the pattern for
in the same file. Worth doing.

### IN-04: `_materialize_suggestions_plex_playlist` builds a URL by string-joining `seed_rating_keys` without validation

**File:** `app/services/suggestions_service.py:263-265`
**Issue:**

```python
def _create_sync() -> Tuple[str, int]:
    plex = PlexServer(plex_url, plex_token, timeout=30)
    key_str = ",".join(str(k) for k in seed_rating_keys)
    tracks = plex.fetchItems(f"/library/metadata/{key_str}")
```

If a `rating_key` ever contains a `/`, `,`, `?`, or any URL-special
character, the resulting path is broken. In practice Plex rating_keys
are numeric strings populated by `sync_service`, so the risk is
theoretical — but the function makes no defensive assertion. A single
`urllib.parse.quote` (or a numeric-validation `int(k)` cast that raises
on garbage) would catch any future ingestion bug at the right layer.

**Fix:**

```python
key_str = ",".join(str(int(k)) for k in seed_rating_keys)
```

Will raise `ValueError` on any non-numeric rating_key — fails loudly at
the call site instead of silently producing a malformed Plex request.

### IN-05: Cost meter "breaker_paused" 60-second window doesn't match the actual trip lockout

**File:** `app/routers/pages.py:357-366`
**Issue:**

```python
if (_dt.now(_tz.utc) - tripped_dt).total_seconds() < 60:
    breaker_paused = True
    breaker_reason = breaker.last_tripped_reason
```

The settings page shows "Suggestions paused" for 60 seconds after any
trip. But the breaker's actual lockout window depends on the reason:
`burst_5_per_60s` clears in 60s, `debounce_30s` clears in 30s, and
`daily_quota_50` clears at UTC midnight (could be 23+ hours away). A
user whose daily quota tripped sees the banner for 60 seconds, then it
silently disappears even though the breaker is still locked.

Minor UI mismatch; not a correctness bug for the breaker itself (the
breaker SELECT will still raise on the next call attempt). Worth fixing
because the cost meter is the user-facing signal that explains why
suggestions stopped refilling.

**Fix:** Render based on the actual lock-until window (the breaker's
`CostBreakerTrippedError.until` field is already an ISO string the
template can compare against `now`), not a hard-coded 60 seconds.
