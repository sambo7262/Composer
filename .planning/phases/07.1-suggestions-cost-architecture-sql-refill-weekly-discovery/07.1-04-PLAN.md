GAP-01 closure (blocking, in-scope for 07.1) — defensive INPUT-side sizing
for the weekly discovery LLM call. NAS UAT 2026-05-16 07:15:44 confirmed
the catch-up gate fires correctly at +10s after startup (Plan 02 D-C2 is
working), but `discovery_call_weekly` then raised
`BadRequestError: prompt is too long: 202027 tokens > 200000 maximum`
from `app/services/suggestions_discovery.py:695`. The OUTPUT-side max_tokens
floor + `MaxTokensTruncationError` retry guard from Phase 7.1 already
exists; this plan adds the symmetric INPUT-side control so a ~10.5K track
cold-start library cannot blow past Claude's 200K input context limit.

Two complementary controls, both required:

1. **Hard `LIMIT` in `_read_discovery_eligible_sync`** ordered by
   `t.last_viewed_at NULLS FIRST, t.id`. Caps the worst-case candidate
   pool at 200 rows. Oldest-unplayed wins (matches the D-A1 rediscovery
   semantic). Deterministic secondary sort on `t.id` so the fixture-based
   test is stable.

2. **Per-prompt token estimator in `discovery_call_weekly`** that runs
   AFTER `_build_discovery_user_prompt` returns. Uses a conservative
   `chars / 3.5` chars-per-token heuristic (Anthropic tokenizer averages
   ~3.5-4 chars/token for English text + structured data; 3.5 is the
   defensive low end). If `estimated_tokens > DISCOVERY_PROMPT_TOKEN_CEILING`
   (= 150_000, leaving 50K headroom below Claude's 200K hard limit), trim
   the candidates list in half iteratively (keeping the oldest-played
   first per the original ORDER BY) and rebuild the prompt until the
   estimate is below ceiling. Log a `logger.warning` on every trim
   iteration recording pre-trim candidate count, post-trim candidate
   count, and final estimated tokens.

Critically the LIMIT in (1) alone is NOT sufficient — if a future change
adds richer candidate metadata to the prompt (e.g., genre + album +
year + tags) 200 rows could STILL exceed 150K. Belt-and-suspenders.
Conversely the estimator in (2) alone is not sufficient either — a
zero-LIMIT query against a 100K-track library would consume DB memory
serialising 100K rows before the trimmer ever ran. Both controls ship
together.

Preserves all Phase 7.1 invariants — AST guards from Plan 03 still pass
unchanged, Phase 5 D-09 `_*_sync` helper boundary still encloses every
`Session(get_engine())`, the SUGG-14 OUTPUT-side `max_tokens=8000` floor
+ `MaxTokensTruncationError` retry guard remain unchanged.

The SQL gets ONE addition at the bottom (before `.all()`):
`ORDER BY t.last_viewed_at IS NULL DESC, t.last_viewed_at ASC, t.id ASC LIMIT :limit`.

SQLite syntax notes:
- SQLite does NOT support `NULLS FIRST` keyword directly in versions
  bundled with the system. Use the portable `ORDER BY col IS NULL DESC, col ASC`
  pattern (puts NULLs first since `IS NULL` evaluates to 1 for null rows
  and 0 for non-null rows, then DESC orders 1 before 0).
- Verified portable since SQLite 3.0; no version dependency.
