# Phase 7.1 Plan 04: GAP-01 Closure — Discovery LLM Prompt Size Bound

**One-liner:** Two complementary input-side controls bound the weekly discovery LLM prompt — SQL `LIMIT 200` ORDER-BY-oldest-unplayed-first plus a per-prompt chars/3.5 token-estimate trimmer with a 150K ceiling — closing the 202K-token blow-up surfaced by NAS UAT 2026-05-16 on a ~10K-track cold-start library.

**Why the two constants ship together (belt-and-suspenders rationale):** The LIMIT alone is insufficient — if a future change adds richer candidate metadata to the prompt (e.g., genre + album + year + tags), 200 rows could STILL exceed 150K tokens. Conversely the estimator alone is insufficient — a zero-LIMIT query against a 100K-track library would consume DB memory serializing 100K rows before the trimmer ever ran. Both controls must ship together.

## SQL ORDER BY Change

Inside `_read_discovery_eligible_sync` (Task 1 GREEN):

```sql
ORDER BY
    CASE WHEN t.last_viewed_at IS NULL THEN 0 ELSE 1 END,
    t.last_viewed_at ASC,
    t.id ASC
LIMIT :limit
```

- **CASE WHEN ... THEN 0 ELSE 1 END:** Portable SQLite NULLS-FIRST emulation (the `NULLS FIRST` keyword is not supported across all SQLite versions bundled with Python). NULL rows sort first (0 < 1), then non-NULL rows by `last_viewed_at` ASC (oldest-played first per D-A1 rediscovery semantic), then `t.id` ASC for deterministic tie-breaks in fixture-based tests.
- **LIMIT :limit:** Parameterized; default `DISCOVERY_CANDIDATE_LIMIT = 200`. Both `_read_discovery_eligible_sync` and `compute_discovery_eligible` carry the kwarg so tests can drive boundary behavior without monkeypatching the module constant.

## Trimmer Block in `discovery_call_weekly`

Inserted between the `user_prompt = _build_discovery_user_prompt(...)` build (line 712) and the credentials-read block (line 716+):

```python
# Runs ONCE before the retry loop; the retry loop below only adjusts
# max_tokens (OUTPUT side), and NEVER re-trims candidates. INPUT-side
# and OUTPUT-side controls are independent.
pre_trim_count = len(candidates)
estimated_tokens = (
    len(system_prompt) + len(user_prompt)
) / DISCOVERY_CHARS_PER_TOKEN_RATIO
trim_iterations = 0
while estimated_tokens > DISCOVERY_PROMPT_TOKEN_CEILING:
    if len(candidates) <= pick_count:
        logger.error(...)  # halt floor — pathological prompt builder
        break
    new_count = max(pick_count, len(candidates) // 2)
    candidates = candidates[:new_count]
    user_prompt = _build_discovery_user_prompt(candidates, ...)
    estimated_tokens = (...) / DISCOVERY_CHARS_PER_TOKEN_RATIO
    trim_iterations += 1

if trim_iterations > 0:
    logger.warning("trimming candidate pool from %d to %d ...", ...)
```

**Halt condition:** `len(candidates) <= pick_count`. Never trim below the number of picks we plan to ask the LLM for — no point asking for 5 picks from a pool of 3. If the estimate STILL exceeds 150K at pick_count rows, the trimmer logs an ERROR and proceeds with what it has (does not infinite-loop, does not raise). Validated by `test_trimmer_halts_at_pick_count` using a pathological `_build_discovery_user_prompt` stub that always returns 600K chars.

**Warning log key:** `"discovery_call_weekly: trimming candidate pool from %d to %d candidates over %d iteration(s); final estimated tokens = %d (ceiling = %d)"`. Asserted by `test_oversize_prompt_trimmed_until_under_ceiling`.

## Decisions Made

| # | Decision | Rationale |
|---|----------|-----------|
| 1 | Portable `CASE WHEN col IS NULL THEN 0 ELSE 1 END` for NULLS-FIRST | SQLite does NOT support `NULLS FIRST` keyword across all bundled versions. The CASE-WHEN pattern is unambiguously portable. The `IS NULL DESC` shortcut also works but CASE-WHEN is more explicit and self-documenting. |
| 2 | `_patch_full_pool` helper patches `compute_discovery_eligible` (not the module constant) | Python default-arg semantics bind `limit=DISCOVERY_CANDIDATE_LIMIT` at function-DEFINITION time. Module-attribute monkeypatching does NOT affect the existing default. The helper monkeypatches the function itself with an explicit `limit=10_000` pass-through. This is plan-checker concern #3 made explicit: without this, the 10K-fixture trimmer test would pass for the wrong reason (SQL LIMIT alone caps at 200; trimmer would never engage). |
| 3 | Marker for "oldest preserved" assertion uses rendered title not plex_rating_key | The rendered `user_prompt` format is `f"track_id={c['track_id']}: {c['artist']} — {c['title']} (last_played=...)"` — no `plex_rating_key` field. "Candidate Title 9999" is the i=9999 title (oldest); "Candidate Title 0" is the i=0 title (youngest). Both are unique substrings inside the rendered prompt. |
| 4 | TasteProfile fields in `_seed_n_candidates` mirror existing `_seed_discovery_environment` helper byte-for-byte | Plan-checker concern #1 — read `app/models/taste_profile.py` first; the fields are `id`, `rated_track_count`, `centroid_*`, `top_artists_json`, `top_genres_json`, `summary_text`, `computed_at`. The existing helper at line 605 already uses the correct field names — mirrored exactly. |
| 5 | Trimmer block runs ONCE before the retry loop | Plan-checker concern #2 — the OUTPUT-side `MaxTokensTruncationError` retry doubles `max_tokens` but does NOT re-trim candidates. INPUT-side (trimmer) and OUTPUT-side (retry loop) controls are independent. Added a one-line comment in the trimmer header making this explicit, plus reinforced it in the GAP-01 SUMMARY tech-stack patterns section. |

## Deviations from Plan

### Minor Drifts (Auto-resolved)

**1. [Rule 1 — bug] Plan-text `monkeypatch DISCOVERY_CANDIDATE_LIMIT to 10_000` does not work**

- **Found during:** Task 2 GREEN initial test run.
- **Issue:** The plan's STEP 3 for Task 2 said: "Easier: monkeypatch `DISCOVERY_CANDIDATE_LIMIT` to 10_000 for this test only, so the full 10K candidate pool reaches the trimmer." Python default-arg semantics bind `limit=DISCOVERY_CANDIDATE_LIMIT` at function-definition time, so monkeypatching the module attribute has no effect on the function's existing default. The 10K-fixture test failed at the trimmer-fired assertion because only 200 rows ever reached the trimmer.
- **Fix:** Introduced a `_patch_full_pool` helper that monkeypatches `compute_discovery_eligible` itself to an async wrapper that explicitly passes `limit=10_000` through to `_read_discovery_eligible_sync`. The helper is named, has a docstring explaining the Python-semantic constraint, and is called explicitly by both 10K-fixture tests with a comment quoting plan-checker concern #3.
- **Files modified:** `tests/test_suggestions_discovery.py`
- **Verification:** Both 10K-fixture tests now pass; `caplog` captures the trimmer's WARNING log; the oldest-preserved assertion sees `Candidate Title 9999` in the captured prompt.
- **Commit:** `20236cb` (Task 2 GREEN)

**2. [Rule 1 — bug] Plan-text suggested searching for `plex_rating_key` in rendered user_prompt**

- **Found during:** Task 2 GREEN initial test run.
- **Issue:** The plan's `test_trimmed_prompt_preserves_oldest_first` assertion called for `track_id=9999` / `track_id=0` markers inside the rendered user_prompt. But `_build_discovery_user_prompt` doesn't render `plex_rating_key`; it renders `track_id={c['track_id']}: {c['artist']} — {c['title']}`. Track IDs are auto-assigned by the DB, not the seed index `i`, so `track_id=9999` does NOT correspond to the i=9999 row.
- **Fix:** Switched markers to use the rendered title `Candidate Title 9999` (i=9999 oldest, padded with 40 'x' chars per `_seed_n_candidates`) and `Candidate Title 0 ` (i=0 youngest, trailing space to avoid matching `Candidate Title 0xxx` prefix collisions if any). Verified both markers appear-or-not in the actual captured prompt output.
- **Files modified:** `tests/test_suggestions_discovery.py`
- **Verification:** Test now passes; oldest seeded track survives the trim, youngest does not appear.
- **Commit:** `20236cb` (Task 2 GREEN)

**Both deviations are Rule 1 bug fixes (test would have falsely failed for unrelated reasons); neither expands scope nor weakens any invariant.** The fundamental control behavior is exactly what the plan specified — `DISCOVERY_CANDIDATE_LIMIT` constant + SQL LIMIT, plus per-prompt chars/3.5 trimmer with 150K ceiling, plus halt-at-pick-count safety floor.
