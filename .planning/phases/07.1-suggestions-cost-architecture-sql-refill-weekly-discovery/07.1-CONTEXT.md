<domain>
## Phase Boundary

Replace Phase 7's per-event LLM refill (`refill_suggestions_queue`, ~$0.05/play, trips $0.42 daily breaker after 8 plays — confirmed NAS UAT 2026-05-14 16:51 UTC) with a hybrid:

1. **SQL-driven refill in the hot path** against Phase 6's pre-computed `TrackVibe.distance`. Free, instant on every drain.
2. **Weekly LLM "discovery" call** that injects 3–7 tracks owned but unplayed in 90+ days, fitting the user's taste.

Drops steady-state cost from ~$150/mo to ~$0.20/mo while preserving Phase 7's "AI-curated" property.

This phase REPLACES Phase 7's `refill_suggestions_queue` — it does not extend it. The mirror itself, the drain hook, and the `Composer · Suggestions` Plex playlist materialization all stay as-is.

<decisions>
## Implementation Decisions

### Area A — Discovery Semantics

**D-A1 — Discovery-eligible = owned tracks unplayed in 90+ days.**
A track is discovery-eligible if `Track.last_viewed_at IS NULL OR Track.last_viewed_at < (now - 90 days)`. Catches both "never tried" and "fell off the rotation". Matches typical rediscovery cadence.

**D-A2 — LLM context = discovery-eligible subset + cached taste profile.**
The weekly prompt sends the candidate pool (filtered by D-A1) plus the cached taste profile (Phase 6.2 vibes). Does NOT send full library. Keeps prompt small and bounded; LLM picks from a pre-narrowed list.

**D-A3 — Adaptive pick count, 3–7 based on plays since last batch.**
Heavy listening week → more discovery (up to 7). Light week → fewer (down to 3). Requires a `plays_since_last_discovery` counter incremented on every `handle_track_played` and reset on successful discovery call. Mapping (planner can refine): 0–10 plays → 3 picks, 11–25 → 5, 26+ → 7.

### Area B — SQL Hot-Path Refill Semantics

**D-B1 — Cross-vibe pool weighted proportional to library share.**
Pull from all vibes proportional to their size in the rated library. If 40% of rated tracks live in "Late Night", ~12 of the 30 picks come from there. Reflects overall taste shape; does NOT require detecting "current vibe" from a play event (avoids the multi-vibe-membership problem).

**D-B2 — Order by `TrackVibe.distance` ascending + light randomization within top ~100 per vibe.**
Within each vibe's allocated slot count (per D-B1), select randomly from the top ~100 closest-to-centroid tracks. Variety without destroying taste-fit. Concrete tunables (planner refines): `TOP_N_PER_VIBE = 100`, `RANDOM_SEED` derived from current timestamp so refills aren't deterministic across plays.

**D-B3 — Discovery picks mix into the SQL pool naturally; no pinning, no separate UI shelf.**
Once the weekly discovery call writes its picks, they live in the same candidate pool the SQL refill reads from. No `is_discovery` flag on the mirror, no separate UI column, no "Discovery" badge. Keeps the model + UI simple. They surface organically when SQL ordering picks them up.

### Area C — Schedule & Resilience

**D-C1 — Hardcoded Sunday 03:00 UTC weekly cron via APScheduler.**
Mirror the existing `sync_scheduler.py` APScheduler pattern (already runs library sync + soft-negative sweep). One scheduled job: `discovery_call_weekly`, fires Sunday 03:00 UTC. Off-peak for US timezones; aligned with existing infrastructure. NOT configurable in v1 — change requires code edit.

**D-C2 — Catch-up on app startup if >7 days since last successful run.**
On every Composer startup, read the last successful `discovery_call_weekly` timestamp from `MigrationLog` (or a new dedicated table). If `now - last_success > 7 days`, fire one immediately. Handles the NAS-asleep-on-Sunday case without complicating the scheduler. Resilient by design.

**D-C3 — Failure mode: log + retry next week. No SQL fallback for "pseudo-discovery".**
If the weekly LLM call fails (timeout, parse error, breaker tripped, network), log a structured `LLMUsage` row with the error and exit. The SQL hot path keeps the mirror full regardless — the user never sees an empty playlist. Next Sunday tries again. NO fallback "pseudo-discovery" SQL pick (rejected because it would mask discovery failures from observability).

### Area D — Migration & Cleanup

**D-D1 — Delete `refill_suggestions_queue` entirely. Delete the orphaned constant too.**
Remove `refill_suggestions_queue` and its 4 call sites from `app/services/suggestions_service.py`. Remove the 2 sites in `maybe_schedule_refill` and `handle_track_played` that invoke it. Remove the orphaned `SUGGESTIONS_RANK_MAX_TOKENS = 8000` constant introduced by quick task `260514-e6w` (no longer referenced). Migrate or delete the regression tests in `tests/test_suggestions_service.py` that pin the constant. Clean removal — no feature flag, no dormant code.

**D-D2 — Leave existing Phase 7 `MigrationLog` row + populated `SuggestionsMirror` data alone.**
The Phase 7 `MigrationLog` row is historical truth ("Phase 7 ran on this date"). Add a NEW `MigrationLog` row for Phase 7.1's bootstrap (dedicated migration ID like `phase_07_1_sql_refill_bootstrap`). Existing `SuggestionsMirror` rows from current testing drain seamlessly via the new SQL refill — no data migration, no wipe. User-visible result on deploy: mirror keeps current contents, drains naturally, refills now use SQL ordering.

**D-D3 — Repurpose `DAILY_COST_BUDGET_USD` as a weekly-call guard, not removed.**
Lower the budget to a weekly threshold appropriate for the new model (planner suggests `WEEKLY_DISCOVERY_BUDGET_USD = $0.50` or `$2/month`). Defends against a future regression putting the LLM back in a hot loop. Keeps the `/debug/suggestions` cost breaker UI panel intact (just with new framing). Constant gets renamed; the cost meter logic stays.
